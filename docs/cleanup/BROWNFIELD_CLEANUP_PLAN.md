# InternAgent 阶段性棕地清理与架构提升方案

更新日期：2026-08-01。

本方案用于对已经持续开发一段时间的 InternAgent 仓库进行一次可回滚、可解释、分阶段的清理与架构提升。

本方案的目标不是追求删除文件数量，而是先建立可信的代码事实，再识别可以安全处理的候选，最后由人工确认删除范围。

## 一、执行原则

1. 先建立事实，再提出删除候选，最后才讨论删除。
2. 源代码、上游代码、生成物、运行时数据、测试夹具和历史归档必须分开判断。
3. 静态分析没有引用不等于代码一定可以删除，因为项目可能存在配置入口、动态导入、CLI 入口、任务目录约定、插件注册和子进程调用。
4. 现有未提交改动属于用户工作，不覆盖、不回滚、不混入清理补丁。
5. 本轮默认只生成文档、基线和候选清单，不自动删除用户代码或产物。
6. 每个删除候选都要留下路径、理由、证据、风险、置信度和人工确认状态。
7. 质量门优先阻止新增问题，不要求一次性清零历史债务。
8. 所有机械迁移都必须能够通过小范围 diff、测试和回滚说明进行审查。
9. 如果架构分析需要的工具未安装，可以在本机全局安装，但必须记录安装方式、版本和实际执行命令。

## 二、分析边界

仓库内容先分为以下六类。

| 类别 | 含义 | 默认处理方式 |
| --- | --- | --- |
| source | 当前产品或研究运行时的第一方源码 | 进入架构、死代码和依赖分析 |
| vendored | 外部项目或上游复制进来的代码 | 默认不删除、不重构，只做边界和许可证审计 |
| generated | 由构建、代码生成或工具自动产生的文件 | 默认不作为人工源码候选，检查生成来源 |
| runtime-data | 日志、缓存、结果、截图、临时运行目录和数据库 | 与源码债务分离，单独判断保留、忽略或归档 |
| fixture | 测试输入、实验样例和复现数据 | 先确认测试或任务入口，再判断是否可归档 |
| archive | 明确标记为历史记录、旧原型或过期迁移材料的内容 | 只有在确认没有文档和复现价值后才提出删除 |

当前仓库中的 `third_party`、`desktop/openworker/upstream`、`results`、`logs`、`tmp`、缓存目录和 `.scratch` 原型默认不进入第一轮删除候选。

## 三、推荐技能组合

### 1. 架构发现

使用 `improve-codebase-architecture` 扫描近期变动热点、浅模块、耦合泄漏和难以测试的接口。

该技能只提出候选，不直接删除代码。

使用 `codebase-design` 统一使用 module、interface、depth、seam、adapter、leverage 和 locality 这些架构概念。

### 2. 事实图和运行时核对

使用现有 `codebase-memory-mcp` 建立并刷新文件、符号、调用、导入、路由、测试和配置关系图。

使用 `verify-local-runtime` 核对真实启动入口、监听端口、HTTP 路由、配置加载、日志和运行时产物。

运行时核对用于防止把静态图看不到的动态入口误判为死代码。

### 3. 死代码和依赖候选

Python 使用 Vulture 发现未使用函数、类和变量候选。

Python 使用 Ruff 发现未使用导入和低风险代码问题。

Python 使用 deptry 检查依赖声明与实际使用之间的差异。

TypeScript 和 JavaScript 使用 Knip 发现未使用文件、导出和依赖。

TypeScript 和 JavaScript 使用 dependency-cruiser 检查循环依赖和越层依赖。

使用 scc 建立文件数、代码行数、复杂度、重复度和 Git 活跃度基线。

使用 ast-grep 进行结构化搜索和可回滚的机械迁移。

这些工具只能生成候选，不能单独授权删除。

### 4. 类型、边界和增量质量门

Python 在可控目录中选择 Pyright 或 mypy 作为类型安全网。

前端使用 ESLint 和 typescript-eslint 约束新增代码。

Python 模块边界使用 Import Linter，前端模块边界使用 dependency-cruiser。

使用 Semgrep 编码旧 API、越层导入、危险子进程、路径操作和缺少 schema 的工具注册规则。

使用 reviewdog 只把本次改动新增的问题反馈到代码审查中。

### 5. 计划、测试和收尾

使用 `tdd` 为每一个删除或重构候选建立行为回归测试。

使用 `request-refactor-plan` 把确认的架构候选拆成小步、可回滚的提交。

使用 `code-review` 分别审查代码规范和原始目标是否被正确实现。

使用 `staged-git-sync` 只同步已经验证的产品文件，不把缓存、日志、临时文件和无关工作混入提交。

## 四、阶段性执行顺序

### 阶段 0：冻结边界并记录基线

记录当前分支、HEAD、工作树状态、工具版本、配置文件和已存在的用户改动。

如果发现必要工具缺失，先检查本机已有的 Homebrew、Python、pipx 和 npm 环境，再选择合适的全局安装方式。

所有新增工具都要在报告中标记为“本轮安装”，并记录版本，避免把工具缺失误认为项目没有问题。

记录源代码、上游代码、生成物、运行时数据、夹具和归档目录的分类结果。

保存一次可重复运行的规模和复杂度基线。

成功标准是任何人都能知道本轮分析覆盖了什么，以及明确排除了什么。

### 阶段 1：建立代码图和入口目录

刷新 `codebase-memory-mcp` 索引，并记录索引时间、commit SHA、节点数量、边数量和排除目录。

收集 Python、TypeScript、Rust、Bash 和配置文件的入口信息。

登记 CLI、HTTP 路由、动态导入、模型工具注册、任务目录约定、子进程和构建入口。

成功标准是候选代码可以追溯到引用、入口或明确的无入口证据。

### 阶段 2：生成清理候选

运行 Vulture、Knip、Ruff、deptry、dependency-cruiser、scc 和图谱死代码查询。

把结果分成“高置信度可确认”、“需要人工核对”和“只观察不删除”三类。

优先处理无用依赖、无引用导出、重复配置和明确的临时产物。

暂不处理动态任务、上游代码、实验夹具和不清楚所有权的目录。

### 阶段 3：锁定架构边界

选择最重要的模块关系，写成 Import Linter、dependency-cruiser、ESLint、Semgrep 或测试规则。

规则默认只阻止新增违规，历史违规使用基线和豁免记录管理。

成功标准是新代码不会继续扩大已经确认的边界问题。

### 阶段 4：执行小步迁移

对确认的结构性重复使用 ast-grep、Ruff autofix 或 jscodeshift 等确定性工具。

每个补丁只处理一个模式或一个模块，并包含测试、构建、smoke 或 E2E 验证。

任何删除动作都要在人工确认后单独执行，不与架构重构混为一个大 diff。

### 阶段 5：运行时确认和持续治理

对静态分析认为可能无用的模块观察真实入口和运行路径。

对依赖使用 Renovate、Dependabot 或 OSV-Scanner 形成后续维护节奏。

每个阶段结束后重新生成基线和候选清单，比较变化而不是只看删除行数。

## 五、删除候选的确认门槛

一个候选至少需要满足以下五项证据中的四项，才可以进入“建议删除”列表。

1. 代码图中没有调用者、导入者、测试或已知入口。
2. 配置、CLI、路由、动态导入、任务约定和子进程搜索没有发现入口。
3. 相关测试、smoke 或 E2E 验证通过，且删除后有明确回滚方式。
4. 最近运行时观察窗口没有命中该模块或其产物。
5. Git 历史和文档没有显示它仍承担当前产品契约。

不满足门槛的内容只能列为“待确认”或“暂不删除”。

## 六、最终报告格式

最终报告使用通俗语言解释每一个参数和判断。

报告至少包含当前基线、分析范围、工具结果、架构候选、死代码候选、产物候选、暂不删除项、风险和建议顺序。

每个候选使用以下字段：路径、它看起来是什么、为什么被发现、有哪些证据、可能影响什么、置信度、建议动作和需要用户确认的问题。

报告不会把“工具没有找到引用”表述成“确定可以删除”。

## 七、本轮明确不做的事情

不删除用户已有的工作树改动。

不重写 `CHANGELOG.md` 或自动生成文件。

不自动修改上游 OpenWorker 代码。

不为了追求更少文件而迁移整个构建系统。

不把大规模 AI 自动改写当成架构治理方案。

不在用户确认前执行任何实质性删除。
