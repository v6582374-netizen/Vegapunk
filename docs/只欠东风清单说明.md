# 只欠东风：五件必须由人做的事

这份文档解释 `run_operation.py readiness` 打印的那五条。

每条都按同一格式写：**要你做什么 → 为什么代码做不到 → 不做会怎样 → 做完了怎么算完**。

先说一句总的。这五件事没有一件是"程序还没写完"。它们全都是**房间里的物理动作**：装一个补丁、观察一次机器人、标定一个相机、插两个相机、录几十遍。软件那一侧已经在等着了——`vegapunk/operation/` 有 12 个模块、224 个测试全绿、整条执行路径在没有机器人的情况下端到端跑通过。

这一版有两处是你指出来后改的，改的是**代码**不只是文档：操作台是死的，不报任何状态，所以"先问仪器自报"那条路径根本不存在，已删除；天平也已经从硬性要求降为可选项，判定改为肉眼三档。

配套阅读：[具身操作 harness 名词解释](具身操作harness名词解释.md)。下面出现的 tracker、safe hold、witness、Episode Outcome 等词，那份文档里都有从零开始的解释。

---

## 为什么会有"只欠东风"这种状态

正常写软件，你写完就能跑。这里不行，原因很简单：

**这套系统的正确性依赖于物理世界的事实，而那些事实不在代码里。**

举个最直白的例子。系统里有一条规则："如果视觉丢了目标，就保持（hold）"。这条规则的代码是十几行，早就写好了。但"保持"到底安全吗？取决于一个谁都没测过的事实——**当你停止给 G1 下发全身指令时，它的固件会不会自己进入阻尼状态**？

- 如果会：那停止发令只是"机器人软软地站住"，不理想但不致命。
- 如果不会：那停止发令就是**没有任何东西在维持平衡**，机器人直接倒。

这两种情况下，同一段代码的含义完全不同。而这个事实**只能靠把机器人吊起来、真的停一次发令、然后用眼睛看**来获得。没有任何静态分析、任何文档、任何仿真能替代它。

所以这五条不是待办事项列表，而是**这套系统与现实世界之间还没连上的五根线**。

## 第 1 条：把 dead-man 装进 tracker 的控制环

### 要你做什么

两条命令：

```bash
python3 scripts/patch_twist2_deadman.py --check   # 先看它要改什么，不写文件
python3 scripts/patch_twist2_deadman.py           # 真的改
```

脚本会自动备份原文件（`.orig`），可以 `--revert` 撤回，重复运行不会改第二次。

### 为什么代码做不到

因为要改的文件**不在这个仓库里**。它在 `~/TWIST2-master/deploy_real/server_low_level_g1_real.py`——那是厂商给的代码，是真正驱动机器人的那个 50 Hz 循环。

我可以生成补丁，可以验证补丁后的文件语法正确、危险代码被移除，但**把厂商代码改掉这个决定应该由人按下**。

### 不做会怎样

这是五条里唯一一条**现在就是危险的**。

厂商那个循环长这样（简化）：

```python
while True:
    读取 Redis 里的四个 key
    action = json.loads(读到的东西)     # ← 问题在这
    发给机器人的关节
```

如果上游程序死了，Redis 里的 key 就没了，读出来是 `None`。`json.loads(None)` 会抛异常。异常被循环外层的兜底 `except` 抓住，然后走到 `close()`——而 `close()` 的实现是 `exit()`。

连起来看就是：

> **上游程序一死，正在维持机器人平衡的那个进程就退出。**

在一台正站着的双足机器人上，这不是"停止"，这是**摔倒**。

补丁把那段读取换成一次调用，它永不抛异常、永不返回空：读不到、过期了、序号倒退了，全都变成"发布一个站立目标"。

### 做完了怎么算完

再跑 `readiness`，第一条会从"需要人做"变成：

```
+ dead-man is installed in the vendored 50 Hz loop
```

## 第 2 条：测量"停止发令时机器人会怎样"

### 要你做什么

把机器人**吊起来或以其他方式固定住**（脚不承重），然后观察三件事：

1. 正在发令的过程中，**停止发令**，机器人怎么反应？多久？
2. 遥控器的**阻尼组合键**按下去，从一个正在受控的状态出发，产生什么效果？多久？
3. 这两种情况，事后软件能不能看出来发生过？

把结果连同测量条件一起记下来。

### 为什么代码做不到

这是**读代码永远得不到答案**的一条。我查过厂商代码：Python 这一层没有发出任何阻尼指令，`close()` 就是 `exit()`。但机器人**固件**里有没有自己的保护逻辑，源码里看不见——那在机器人内部，不在这个仓库里。

厂商文档里有一句泛泛的"会进入阻尼"，但那句话不能当作**这个 checkout、这台机器**的证据。

### 不做会怎样

不会立刻出事，但**整个安全设计的价值是未知的**。

我设计了"闭锁"（latch）机制：一旦触发保持，就锁住，直到有名有姓的人来解锁。这个机制值多少钱，完全取决于第 2 条的答案：

- 如果固件有阻尼保护 → 进程意外死亡是"糟糕但可控"，闭锁是锦上添花。
- 如果没有 → 进程意外死亡是**灾难**，闭锁和第 1 条的补丁是唯一防线，必须严格对待。

在知道答案之前，**不应该让任何策略持有运动权限**。

### 做完了怎么算完

有一份写下来的观察记录，包含测量条件。这是 map 里 ticket 12 的内容。

## 第 3 条：架一台台面相机看盖子

### 要你做什么

把一台相机固定下来对着仪器，然后读出两个数：

1. **固定相机**（三脚架、夹具、支架都行，要点是它之后不能被碰动）。
2. **指出画面里哪一块区域随盖子开合而变**。
3. 在**这个房间的真实光照下**，分别在盖子开着和关着时读出这块区域的亮度数值，
   得到两个阈值——中间要留一段空隙。
4. 记下它多久出一个结果。

`GeometricWitness` 就是等这几个数的适配器，除此之外它什么都不需要。

### 为什么代码做不到

**这一条我先前写错了，你指出来是对的。**

我原来把它写成"先问仪器自己报不报状态，报了就归零"。但这台操作台是**死的**——
一块带按钮的面板，没有数字输出、没有串口、没有网口，不会吐出任何状态。
那个"归零"的分支根本不存在，我不该把它写成首选路径。

所以固定相机不是**退路**，它是**唯一的路**。而代码做不到的部分很朴素：
把相机固定在哪、画面里哪块区域、这个房间的灯光下两个阈值是多少——
这些是拿着相机站在那张桌子前才能得到的数。

（顺带：那个适配器类我已经改名为 `BooleanProbeWitness`，因为它的真实用途是
"包一个返回真/假的探针"。如果你以后愿意在盖子上贴一个接触开关或霍尔传感器，
它比相机更可靠，而那时用的就是这个类。）

### 不做会怎样

**整个回路里唯一不可逆的动作没人看着。**

回到设计：这套系统只守一个门——倒水。因为开盖错了能再关，抓杯失败能再放，
按钮按错能再按，但**水一旦倒出去就收不回来**。而"往关着的盖子上倒水"
是这个回路里真正会造成破坏的失败。

守这个门需要一个比特：盖子开着吗？关键是这个比特**不能来自策略自己的眼睛**。
理由很直接：

> 如果监视器和被监视者用同一个相机、同一个模型，那一次感知失败会同时干掉两个。
> 该保持的时候，恰恰不会保持。

而且更糟——如果策略能看见这个证据，它会**学会盯着这个证据**，
于是监视器变成了它要约束的那个行为的一部分。

**这里也是"人说的不算"唯一真正成立的地方。** 闸门要在机器人正在动的时候，
批准一个不可逆的动作。人来不及、也不该在这个位置上当传感器。
所以它需要一个人无法插手的通道——这跟事后判断结果是两件完全不同的事，
下面第 4 条会讲到。

### 做完了怎么算完

有一个能报出 `open` / `closed` / `indeterminate` 三种值的通道，
知道它的更新频率，知道它掉线时怎么发现，并且把相机位姿记下来
（挪动它会让之前采的数据不再适用于新布置）。这是 ticket 15。

## 第 4 条：接上腕部相机

### 要你做什么

把两个腕部相机接进录制流程，让它们和头部相机一起被记录。

### 为什么代码做不到

代码不能把相机插上。

### 不做会怎样

**这里有一个我用真实数据发现的坑，值得单独说。**

现有录制文件是 480×1280 像素。看起来像"两个相机并排"，我一开始也这么以为。但我实测了两个半幅的相关性：约 0.72，而且**最佳水平位移随画面内容变化**——在同一段视频的三帧上分别是 16、30、12 像素。

那个变化的位移就是**视差**。所以这两半不是两个相机，而是**同一个头部相机的左右目**（立体像对）。

两个后果，都很实际：

- 如果直接把整张 480×1280 喂给视觉编码器，它会把并排的一对图当成一张图，学到的是**画面正中间那条缝**的特征。现在改成两个具名视图，各带自己的裁剪框。
- **这一对是一个相机**。如果算成两个，系统就会报告"三相机要求快满足了"，而实际上**两个腕部相机根本不存在**。

数据契约要的是头部 + 左右腕，三个。现在只有头部一个。

腕部相机为什么非要不可：抓杯子、对准按钮这些动作，头部相机的视角是俯视且远，手在画面里又小又常被遮挡。腕部相机看的是"手正要碰到的那个东西"，这是精细操作的主要反馈。

### 做完了怎么算完

`convert` 报告里 `cameras=` 从 `['head']` 变成三个，对应那条溯源缺口消失。这是 ticket 02。

## 第 5 条：采集 pilot 数据，每回合带复位记录和判定

### 要你做什么

用遥操作采集若干回合完整的"走过去 → 开盖 → 倒水 → 放杯 → 关盖"，每一回合都要有：

- **复位记录**（`ResetRecord`）：谁做的复位、什么时间、盖子关好了吗、容器归位了吗、地面和线缆归位了吗。杯子起始液量是**可选**的，想记就记。
- 同步的**头部 + 双腕**画面
- 每一帧的**见证值**（盖子当时的状态）
- 一个**判定**（`EpisodeOutcome`）：回合结束后**看一眼容器**，从 `transferred` / `partial` / `none` 里挑一个，签上自己的名字

最后一条只要几秒钟。**不需要天平。**

### 为什么代码做不到

这是唯一一条**必须由人的身体完成**的：有人穿着遥操作设备，真的驱动机器人走过去、按按钮、端起杯子倒水。数据从人身上来。

判定也必须由人做，但**便宜得多**。这里要区分两件事，它们看起来像同一个让步，其实不是：

| | 闸门（第 3 条的见证） | 判定（这一条的结果） |
|---|---|---|
| 什么时候 | 机器人**正在动**的时候 | 回合**已经结束** |
| 授权什么 | 一个**不可逆**的动作 | 什么都不授权，只是打分 |
| 有东西在等它吗 | 有，机器人下一帧等它 | 没有，机器人早就停了 |
| 人的话算证据吗 | **不算**，永远不算 | **算**，这就是它的设计 |

闸门不能用人的话，因为一个赶时间的人会点"开着吧"，而机器人会立刻把水倒到关着的盖子上。判定可以用人的话，因为它**不授权任何东西**——它只决定这条数据要不要进训练集。

我早先把这两件事混成了一件，要求每个回合都填质量和天平分辨率。那是**误用的严谨**：把实验室计量搬进了行为标签，让"拥有天平"变成采集机器人数据的前置条件，还去量毫升——而这个标签唯一被问到的问题是"倒进去了 / 倒了一部分 / 没倒进去"。**天平量的是水，我们要标的是行为。** 已经改掉了。

### 不做会怎样

**现有的 6 段数据全都不是训练级的，而且差得比想象中远。**

我实测了这 6 段（共 10531 帧）：

| 回合 | 帧数 | 净位移 | 路径长度 |
|---|---|---|---|
| episode_0004 | 2573 | 0.12 m | 2.43 m |
| episode_0007 | 2606 | 0.20 m | 1.91 m |
| episode_0008 | 1428 | 0.27 m | 2.39 m |
| episode_0009 | 1210 | 0.11 m | 1.68 m |
| episode_0010 | 1382 | 0.25 m | 2.08 m |
| episode_0012 | 1332 | 0.05 m | 1.35 m |

它们的任务描述写着 "walk ahead 1 meter"（向前走一米）。但**净位移只有 0.05 到 0.27 米**，而路径长度有 1.35 到 2.43 米。

翻译一下：**机器人在原地挪步，从来没有真的走到哪里去**。根部高度全程 0.87–0.90 米，说明它一直站着——这是站立记录，不是行走记录。

除此之外还缺：没有见证值、没有复位记录、没有判定标签、只有头部相机。

这四条缺口是系统**自己报出来的**，而且会一路带进 checkpoint。所以现在训出来的模型会诚实地把自己标记为 `deployable=False`，任何人都不可能误部署它——这是设计出来的，不是巧合。

### 做完了怎么算完

`convert` 报告最后一行从一串 `NOT training-grade` 变成 `training-grade: yes`。这是 ticket 05。

## 五条之间的依赖关系

它们不是平的，有先后：

```
第 1 条（装补丁）  ──┐
                     ├──→ 才敢让策略持有运动权限
第 2 条（测停止）  ──┘

第 3 条（见证相机）──┐
                     ├──→ 才能采集带标签的数据 ──→ 第 5 条（pilot）
第 4 条（腕相机）  ──┘
```

**第 1、2 条是安全前提**，在它们完成前不该让学出来的策略碰真机。

**第 3、4 条是数据前提**，它们决定第 5 条采出来的数据是不是训练级的。顺序上先做它们，否则采完才发现少字段，就得重采。

**建议的第一步是第 3 条**，因为它是唯一需要动手标定、也最可能反复调的一条：相机位置、图像区域、两个阈值，都得在房间的真实光照下试出来。而且它有个长期负担——见证相机的位姿属于"现场配置"的一部分，挪动它会让之前采的数据不再适用于新布置，所以越早定死越好。

**第 1、2 条和第 3、4 条互不阻塞**，可以并行。

## 最后一句

`readiness` 的结尾那句话是认真的：

> 上面没有任何一条阻碍继续做软件工作。最后那一节的每一项都是房间里的物理动作，而这恰恰是这套 harness 被造出来等待的东西。

软件可以继续往前：慢系统的接口留着但空着、in-run 恢复还在雾里、颈部通道等着被正式接线。但**这五件事没做完之前，这套系统不应该驱动真机**——而它自己会告诉你这一点，不需要你记得。
