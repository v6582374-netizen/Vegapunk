# 从一句研究目标到最终论文

## Vegapunk Discovery 流程机制全景书

> 这不是一份 API 手册，也不是一份普通的“怎样写论文”教程。
> 它要回答的是：当系统收到一句研究目标，以及一份已有的算法和代码基线时，系统内部到底发生了什么，为什么要有 MAS、loop、状态机、记忆、工具调用和 PaperOrchestra，它们怎样把一堆候选想法逐步变成一篇可交付的论文。

本文以当前 Vegapunk 的 Discovery 主链路为准，使用科研探险队和论文工坊的故事来解释机制。文中会同时给出概念层和实现层名称，例如：

- 总协调者（MAS / OrchestrationAgent）
- 工作流状态（WorkflowState）
- 会话账本（WorkflowSession）
- 工具循环（ModelToolLoop）
- 研究草稿捕获器（ResearchDraft）
- 论文编排器（PaperOrchestra）

名称里的英文是为了帮助读者把故事中的角色和系统中的机制对应起来，不要求读者会读源码。

## 阅读前的三个约定

### 约定一：主线是全自动运行

本文不把人工审批、实时人工反馈或 human-in-the-loop 当作主流程。系统可能保留一个名为 AWAITING_FEEDBACK 的状态，但在当前自动运行语境下，它表示“自动反馈插槽”：外层驱动器在交接点读取预先准备好的离线反馈，再把反馈注入流程，继续运行。它是一个状态交接点，不是等待人点击“批准”的按钮。

### 约定二：论文不是某一次模型回复

最终论文是多次结构化加工的结果：

~~~text
研究目标
  -> 候选想法
  -> 批评与证据
  -> 方法规格
  -> 代码实验
  -> 指标与报告
  -> 研究材料包
  -> 论文大纲
  -> 章节、图表与引用
  -> 内容审查与格式修正
  -> TeX 与 PDF
~~~

其中任何一层都可能失败、重试或留下警告。成功不等于“模型说得像真的”，而是要有可以回查的产物和证据。

### 约定三：稳定机制和可变细节要分开

以下内容属于稳定的机制边界：

- Discovery 先于论文交接；
- MAS 用阶段和状态管理想法；
- 工具结果会返回模型上下文；
- 实验结果会形成下一轮的代码或经验反馈；
- ResearchDraft 以追加方式保存可观察过程；
- PaperOrchestra 只在 Discovery 汇总完成后接手。

以下内容可能随着配置或版本变化：

- 默认轮数、并发上限和每个 Agent 的模型绑定；
- 某些文件的具体字段；
- 论文模板和个别审查步骤；
- 是否开启某个可选 Agent。

所以读者应把本文当作“机制地图”，不要把某个默认数字当作永远不变的规定。

## 每个核心模块怎么读

从第二章开始，核心模块尽量使用同一套八格模板：

1. **故事场景**：先用探险队的具体动作建立直觉；
2. **模块职责**：说明这一模块负责什么、不负责什么；
3. **机制拆解**：把关键动作拆成可以追踪的步骤；
4. **状态与循环**：说明它位于哪一层 loop，以及如何进入、重复和结束；
5. **记忆与上下文**：说明它能看到什么、留下什么；
6. **失败与恢复**：说明局部失败如何隔离，运行中断如何继续；
7. **可观察产物**：指出下一阶段真正能读取的文件或结构化结果；
8. **输入—处理—输出小结**：用最短形式复盘整个模块。

阅读时可以先只看每个模块的故事场景和小结，再回头读机制拆解。这样不会一开始就被文件名、状态名和 Agent 名称淹没。

# 序章：研究工坊寄来一封任务信

想象一间叫“星图研究工坊”的实验室。

研究者把一封任务信交给工坊：

> “这是一个已有算法和代码基线。请提出改进方向，验证是否能提升指定指标，记录可靠证据，并形成论文。”

这句话对人类研究团队来说，已经包含了许多隐含工作：

1. 先理解问题、数据、指标和限制；
2. 查找已有方法，避免重复发明；
3. 提出不止一个想法；
4. 评估哪个想法值得做；
5. 把想法变成可以实现的算法方案；
6. 修改代码并运行实验；
7. 读取结果，比较基线，判断是否真的改进；
8. 记录失败和成功的原因；
9. 选择可以讲成一个完整故事的候选；
10. 把事实、数字、方法和证据装配成论文；
11. 编译、检查、修订，交付 TeX 和 PDF。

Vegapunk 的 Discovery 流程，就是把这支“隐形研究团队”显式化。它不是让一个大模型一次性完成十步，而是让多个有明确职责的 Agent 在一个总协调者管理的状态机里协作。

这里有一个关键心智模型：

> Agent 是队员，MAS 是队伍，loop 是反复推进的节奏，状态机是队伍当前所处的房间，记忆是实验室的档案柜，工具是队员可以使用的仪器，产物文件是每个阶段留下的实验记录，PaperOrchestra 是最后的论文编排工坊。

# 第一部：先看全局地图

## 第一章 一次运行中到底有哪些对象

为了不把不同层次的东西混在一起，先给每个对象一个位置。

| 对象 | 故事中的比喻 | 它回答的问题 |
| --- | --- | --- |
| 任务定义 | 任务信、研究委托 | 我们要研究什么？ |
| Launch | 一次探险的总档案夹 | 这次完整运行的边界是什么？ |
| Discovery Round | 一轮探索 | 这一轮从哪个基线出发，试了什么？ |
| MAS Session | 一次研究讨论会 | 这一轮想法如何被提出和打磨？ |
| Idea | 一张研究方案卡 | 这个候选方法是什么？ |
| Candidate Experiment | 一个独立实验工作台 | 这个想法如何被实现和验证？ |
| Run | 一次具体实验尝试 | 这一版代码跑出了什么？ |
| WorkflowSession | 研究会的过程账本 | 当前进行到哪一步，历史发生了什么？ |
| ResearchDraft | 原始实验记录本 | Agent、工具和日志实际留下了什么？ |
| Discovery Summary | 探险总结 | 所有轮次和候选结果如何汇总？ |
| PaperOrchestra Run | 论文制作单 | 这次论文装配过程的状态是什么？ |
| TeX/PDF | 最终交付包 | 论文能否交付和复现检查？ |

### 一张总图

~~~mermaid
flowchart LR
    A[研究目标与代码基线] --> B[Launch]
    B --> C[Discovery Round]
    C --> D[MAS Session]
    D --> E[候选 Idea]
    E --> F[Candidate Experiment]
    F --> G[指标与实验报告]
    G --> C
    C --> H[discovery_summary]
    H --> I[PaperOrchestra]
    I --> J[TeX]
    J --> K[PDF]
~~~

箭头 G 到 C 表示跨轮反馈：上一轮实验结果会影响下一轮。箭头 H 到 I 表示边界：PaperOrchestra 不在每个候选产生时就开始写论文，而是在 Discovery 汇总完成后一次性交接。

## 第二章 从一句话到可执行任务包

### 故事场景

探险队拿到的任务信可能只有一句话，但队员不能只把这句话原样传给每个 Agent。总协调者先把它放进“任务登记台”，确认目标、数据、基线和评价方式是否齐全。

### 模块职责

任务准备阶段的职责是把自然语言委托整理成一次可追踪的研究输入快照。它不负责提出新想法，也不负责写论文。

### 机制拆解

1. **识别任务类型**
   系统先判断这是普通任务，还是带有科学任务结构的任务。科学任务可能把任务信息和检查清单合并成统一的提示材料。

2. **形成 prompt 快照**
   运行开始时，任务输入会被保存到本次 Launch 目录。以后即使源任务目录发生变化，本次运行仍有自己的输入副本。

3. **确定运行边界**
   外层循环要知道要跑多少轮、每轮是从原始基线开始还是接着最优结果继续。模型运行配置和关键选项也需要在本次运行中保持一致。

4. **建立输出空间**
   Launch 目录成为这次研究的容器。每个 Session、候选实验和最终汇总都放在这个容器的可追踪路径下。

### 状态与循环

任务准备通常只执行一次，但它为所有后续循环提供固定起点。如果输入不完整，流程会在进入 Discovery 前失败；如果只是某个可选材料缺失，系统可能使用降级路径继续。

### 记忆与上下文

本阶段的上下文是任务事实：目标、领域、数据、指标、约束和基线。历史想法和经验可能在后续生成阶段加入，但不能替代任务本身。换句话说，记忆可以帮助“怎样探索”，不能偷偷改写“要研究什么”。

### 失败与恢复

- 缺少任务定义：无法可靠建立 Launch，应直接报错。
- 科学任务材料部分缺失：若可由其他任务材料合并，先规范化；否则保留明确缺口。
- 运行中断：只要 Launch 已建立，后续可以从已有目录和记录恢复，而不必假设一切从零开始。

### 可观察产物

- Launch 目录；
- prompt.json；
- 本次运行的配置快照或等价记录；
- 后续 Session 和实验目录的父路径。

### 输入—处理—输出小结

~~~text
输入：研究目标、基线、数据和约束
处理：识别任务类型、固化提示、建立运行边界
输出：可恢复的 Launch 及任务输入快照
~~~

## 第三章 Discovery 外层循环：一次探险不只走一圈

### 故事场景

第一轮探险结束后，队长不会把所有东西丢掉重新开始。若某种改进确实让指标变好，下一轮会站在新的代码基线上继续；若某条路线失败，失败原因会进入档案，提醒下一轮少走弯路。

### 模块职责

Discovery 外层循环负责把“提出方案—做实验—吸收结果”重复若干轮，直到达到配置的轮数或终止条件。它是跨 Session、跨候选实验的最高层 loop。

### 机制拆解

一轮可以拆成六个动作：

1. **确定本轮 baseline**：决定从原始代码还是上一轮最佳代码出发；
2. **准备本轮上下文**：加入任务描述、历史经验和必要的提示演化结果；
3. **运行 MAS**：产生、批评、查证、演化并排序想法；
4. **执行候选实验**：为 top ideas 创建隔离工作台；
5. **汇总实验事实**：读取机器可读指标和叙述性报告；
6. **形成反馈**：更新经验、选择更好的基线，准备下一轮。

### fresh 与 incremental

| 模式 | 代码起点 | 历史记忆 | 适合的理解 |
| --- | --- | --- | --- |
| fresh | 每轮回到原始基线 | 可以仍然保留 | 比较各轮独立探索的效果 |
| incremental | 使用上一轮最佳结果 | 可以仍然保留 | 让研究方案逐轮累积改进 |

这里有一个容易误解的地方：fresh 只重置代码起点，并不代表清空所有历史记忆。代码分支和认知档案是两条不同的反馈边。

### 状态与循环

外层循环的结束条件是“轮次已完成”或“流程明确终止”。它不等同于 MAS 的内部迭代次数，也不等同于一次 Agent 的工具调用次数。

四种重复的层级如下：

~~~mermaid
flowchart TB
    L0[Discovery Round Loop]
    L0 --> L1[MAS Stage Loop]
    L1 --> L2[Agent-Tool Loop]
    L0 --> L3[Experiment Retry Loop]
    L0 --> L4[Paper Refinement Loop]
~~~

- **Discovery Round Loop**：跨轮寻找更好的方向和基线；
- **MAS Stage Loop**：在同一轮中让想法经过多阶段演化；
- **Agent-Tool Loop**：某个 Agent 为完成一步任务反复调用工具；
- **Experiment Retry Loop**：同一个候选在不同代码尝试和运行中迭代；
- **Paper Refinement Loop**：论文生成后进行内容和格式修正。

前四个构成 Discovery 的核心重复；最后一个发生在交给 PaperOrchestra 之后。

### 记忆与上下文

每轮都有自己的 Session 和候选目录，但可以读取上一轮的：

- 失败与成功经验；
- 历史 Idea；
- 代码基线和指标；
- 任务级记忆摘要。

编排器会把这些内容整理成当前阶段需要的上下文包。Agent 并不会因为“属于同一个 MAS”就自动看到所有历史对话；能否看到信息，取决于它是否被编排器放进当前上下文。

### 失败与恢复

- 某个候选实验失败：通常只标记该候选失败，继续汇总其他候选。
- 整轮中断：保留已完成 Session、实验目录和日志，恢复时从已有记录判断哪些步骤已经完成。
- 论文阶段失败：不应把已经完成的 Discovery 反判为失败；可以基于 Launch 汇总重新触发论文交接。

### 可观察产物

- 每轮的 Session 目录；
- ideas.json；
- 每个候选的实验工作区；
- 每轮结果和经验；
- discovery_summary.json；
- incremental 模式下的最终最佳代码和性能索引。

### 输入—处理—输出小结

~~~text
输入：任务快照、当前 baseline、历史经验
处理：MAS + 候选实验 + 指标比较 + 经验更新
输出：本轮结果，以及下一轮的代码/认知反馈
~~~

# 第二部：MAS 如何组成一支研究队伍

## 第四章 MAS 不是“很多模型聊天”

### 故事场景

研究工坊里有一张圆桌。圆桌中央坐着总协调者，周围是生成员、批评员、资料员、方法工程师、排序员和经验记录员。每个人拿到的是同一个研究任务，但只在自己负责的阶段发言。

### 模块职责

多智能体系统（MAS / Multi-Agent System）的职责是把复杂研究任务拆成互相衔接、可以检查的角色工作，而不是让一个模型同时扮演所有角色。

### 机制拆解

MAS 组装通常包含以下部件：

1. **共享模型运行时**：统一处理模型调用、模型身份和基本运行参数；
2. **AgentFactory**：按角色创建 Agent，避免每个角色各自发明一套运行方式；
3. **MemoryManager**：读取和保存会话、历史想法和经验；
4. **本地工具与远程 MCP 工具**：让 Agent 能查资料、读写文件、调用实验或其他外部能力；
5. **OrchestrationAgent**：决定当前阶段、给每个角色准备输入、收集输出并推进状态；
6. **会话生命周期**：创建 Session、保存轨迹、处理恢复和完成。

共享运行时不意味着所有 Agent 共享一个“脑子”。它只表示请求经过统一的模型入口；角色差异来自职责、提示、上下文和可用工具。

### 角色地图

| 角色 | 双层名称 | 主要问题 |
| --- | --- | --- |
| 生成员 | GenerationAgent | 可以尝试哪些研究方向？ |
| 反思员 | ReflectionAgent | 这个方向哪里可能不成立？ |
| 演化员 | EvolutionAgent | 如何根据批评和证据生成下一代方案？ |
| 方法工程师 | MethodDevelopmentAgent | 如何把方向写成可执行的方法规格？ |
| 精炼员 | RefinementAgent | 怎样补足方法细节并消除已知缺口？ |
| 排序员 | RankingAgent | 在当前证据下哪些候选更值得继续？ |
| 资料员 | ScholarAgent | 外部文献和证据能支持什么？ |
| 调研员 | DR / Deep Research Agent | 如何先建立领域背景和问题地图？ |
| 提示演化员 | PromptEvolver | 下一轮的研究指令怎样更有针对性？ |
| 经验记录员 | ExperienceGenerator | 哪些成功/失败模式可以复用？ |

不是每次运行都会启用所有角色。角色是否参与由任务类型、配置和当前阶段决定。

### 状态与循环

总协调者把一次 MAS Session 看成一个可推进的阶段图。它不会要求所有角色同时完成，也不会因为某个角色输出一段文字就自动跳到最终结果。每个阶段都有进入条件、输入、输出和下一状态。

### 记忆与上下文

每个 Agent 至少有三类上下文来源：

- 任务上下文：研究目标、基线、指标和约束；
- 阶段上下文：前一阶段的 Idea、批评、证据或反馈；
- 历史上下文：记忆模块筛选出的相似想法、实验记录和经验。

编排器负责裁剪和拼装上下文。这样做的目的不是隐藏信息，而是避免把无关的整段历史一次性塞进每个 Agent。

### 失败与恢复

- Agent 单次调用失败：工具循环可以把错误作为可见结果返回，或在上层重试；
- 角色输出格式不完整：编排器可以拒绝推进，保留失败记录；
- 某一候选分支失败：只影响该 Idea，不应让所有候选一起消失；
- Session 中断：依靠会话账本和轨迹恢复已完成阶段。

### 可观察产物

- MAS Session 标识；
- 每阶段的状态变化；
- ideas.json；
- 轨迹记录；
- Agent 输出、工具调用及其结果；
- ResearchDraft 中的原始研究块。

### 输入—处理—输出小结

~~~text
输入：任务与上下文
处理：按角色分工完成阶段性研究工作
输出：带批评、证据、方法和排序信息的 Idea 集合
~~~

## 第五章 AgentFactory 与“共享运行时”的意义

### 故事场景

工坊有一个调度柜。队长不亲自改造每个队员，而是从调度柜取出统一装备的角色卡：所有人使用同一套无线电和档案接口，但职责卡不同。

### 模块职责

AgentFactory 的职责是稳定地创建角色实例，并为它们接入：

- 统一的模型运行时；
- 统一的记忆入口；
- 统一的工具注册；
- 统一的研究草稿捕获钩子。

### 机制拆解

“统一装备”解决三类问题：

1. **配置一致性**：同一 Session 中不同角色使用一致的模型解析和调用边界；
2. **审计一致性**：每个角色的输入、输出和工具活动可以用相同方式记录；
3. **替换一致性**：角色策略可以变化，而上层编排不必知道每个角色的内部实现。

“角色卡”则决定：

- 这个角色什么时候被调用；
- 它应该关注什么；
- 它能看到哪些阶段材料；
- 它需要输出什么结构化结果。

### 状态与循环

Factory 本身不负责推进研究 loop。它只保证“需要某个角色时，拿到一个可工作的角色”。真正的顺序由总协调者和工作流状态决定。

### 记忆与上下文

共享运行时、共享工具和共享记忆不是同一个概念：

| 共享对象 | 共享的是什么 | 不代表什么 |
| --- | --- | --- |
| 模型运行时 | 调用入口和模型配置边界 | Agent 有相同职责 |
| 工具注册表 | 可用能力的目录 | 每个 Agent 都会调用所有工具 |
| MemoryManager | 读写历史的接口 | 所有历史会自动进入提示 |
| ResearchDraft 钩子 | 可观察事件的记录方式 | 会记录模型隐藏思维链 |

### 失败与恢复

若某个角色无法创建，MAS 可以选择降级路径（例如关闭可选调研员），但不能假装角色已经完成任务。必要时应在结果中保留“缺少外部证据”或“该阶段跳过”的事实。

### 可观察产物

- 角色创建记录；
- 角色和阶段的对应关系；
- 统一运行时产生的请求与响应记录；
- 工具与草稿捕获记录。

### 输入—处理—输出小结

~~~text
输入：角色需求、统一运行时、工具和记忆接口
处理：按职责创建并连接 Agent
输出：可被总协调者调用的研究队伍
~~~

# 第三部：状态机与阶段循环

## 第六章 为什么要用状态机

### 故事场景

探险队在地图上不只标“开始”和“结束”，还要标明“正在勘探”“正在核查”“正在实验”“正在返回”。如果队长不知道队伍在哪个房间，就无法判断下一步应找谁、缺什么材料、能否恢复。

### 模块职责

工作流状态（WorkflowState）用有限个明确状态描述 MAS 当前所处的阶段。它把连续的模型活动变成可检查的流程节点。

### 机制拆解

当前关键状态可以理解为：

| 状态 | 大白话含义 |
| --- | --- |
| INITIAL | 研究会已建立，但还没开始提出方案 |
| GENERATING | 正在产生候选 Idea |
| REFLECTING | 正在批评和压力测试候选 |
| EXTERNAL_DATA | 正在补充文献、证据或引用 |
| EVOLVING | 正在根据反馈生成子想法 |
| RANKING | 正在给候选排序并决定下一步 |
| AWAITING_FEEDBACK | 到达自动反馈插槽，等待离线反馈注入 |
| METHOD_DEVELOPMENT | 正在把高排名 Idea 变成方法规格 |
| REFINING | 正在修正方法细节 |
| COMPLETED | MAS 研究会已经完成 |
| ERROR | 流程无法按预期推进，需要保留错误并结束或恢复 |

### 简单状态图

~~~mermaid
stateDiagram-v2
    [*] --> INITIAL
    INITIAL --> GENERATING
    GENERATING --> REFLECTING
    REFLECTING --> EXTERNAL_DATA
    EXTERNAL_DATA --> EVOLVING
    EVOLVING --> RANKING
    RANKING --> AWAITING_FEEDBACK
    AWAITING_FEEDBACK --> GENERATING
    RANKING --> METHOD_DEVELOPMENT
    METHOD_DEVELOPMENT --> EXTERNAL_DATA
    EXTERNAL_DATA --> REFINING
    REFINING --> COMPLETED
    INITIAL --> ERROR
    GENERATING --> ERROR
    REFLECTING --> ERROR
    REFINING --> ERROR
~~~

图里有两种回路：

- 未达到内部迭代上限时，RANKING 经过自动反馈插槽回到下一次生成；
- 进入方法开发后，补证据和精炼方法，最后完成 Session。

### 状态与循环

状态机的作用不是让流程变得僵硬，而是让 loop 有“记忆点”。当进程中断时，可以问：

1. 最后一个稳定状态是什么？
2. 该状态的输入材料是否已落盘？
3. 该阶段是否有部分候选完成？
4. 恢复时应该重做当前阶段，还是从下一阶段继续？

状态本身不是进度的全部；它必须和会话账本、产物文件及轨迹一起判断。

### 记忆与上下文

状态变化后，系统会保存阶段推进和相关结果。下一个阶段只接收适合自己的上下文，例如：

- 反思阶段接收 Idea；
- 外部数据阶段接收 Idea 和待核查问题；
- 演化阶段接收批评与证据；
- 排序阶段接收所有候选的综合信息。

### 失败与恢复

错误状态不是“模型不聪明”的代名词。它可能表示：

- 必需输入没有准备好；
- 工具连续失败；
- 结构化结果无法解析；
- 上层发现状态与产物不一致。

恢复时应以最后一个可信产物为准，不用未保存的内存状态臆测流程已经完成。

### 可观察产物

- 当前状态；
- 已完成轮次；
- top ideas；
- 反馈历史；
- 工具使用情况；
- 时间戳；
- 是否进入方法阶段；
- 状态转移对应的轨迹和日志。

### 输入—处理—输出小结

~~~text
输入：当前状态与阶段材料
处理：按转移条件推进或回到某个 loop
输出：下一状态、阶段产物和可恢复账本
~~~

## 第七章 WorkflowSession：研究会的总账本

### 故事场景

每次讨论会结束，书记员都会在账本上写下：今天研究什么、现在在哪个房间、提出了哪些方案、已经完成几轮、谁被选为重点、收到过什么反馈、用过哪些仪器。

### 模块职责

会话账本（WorkflowSession）保存一次 MAS Session 的动态状态。它把“当前内存里的对象”变成可以保存和恢复的运行事实。

### 机制拆解

账本重点记录：

- 研究任务；
- 当前 WorkflowState；
- 所有 Idea；
- 已完成内部轮次和最大轮次；
- top ideas；
- 反馈历史；
- 工具使用情况；
- 时间戳；
- 是否已进入方法开发。

它不是最终论文，也不是完整聊天记录，而是对流程状态的压缩索引。

### 状态与循环

内部迭代计数和外层 Discovery 轮数分开：

- 外层轮数问“这次 Discovery 已经从多少个代码/实验起点探索过”；
- 内部迭代问“当前 Session 的候选想法经过多少次生成—批评—演化—排序”。

如果把这两个数字混成一个，就会误以为“第 3 轮”一定表示同一个东西。

### 记忆与上下文

恢复时，系统根据账本重新构造任务、Idea、状态和相关阶段上下文。原始轨迹和研究草稿可以进一步帮助核对细节，但账本提供的是“从哪里继续”的主线。

### 失败与恢复

账本和文件产物不一致时，系统应优先采取保守策略：

- 已有最终产物但账本未标完成：可以重新验证后补记；
- 账本标完成但必需产物不存在：不能只看状态跳过；
- 某个候选缺失：只恢复已知候选，并记录缺口。

### 可观察产物

Session 目录下的结构化状态记录、ideas.json、轨迹文件以及对应日志。

### 输入—处理—输出小结

~~~text
输入：阶段事件、Idea 变化、工具和反馈结果
处理：更新状态、计数和索引
输出：可保存、可恢复的 Session 账本
~~~

# 第四部：一个 Idea 是怎样长出来的

## 第八章 生成：先扩大搜索面

### 故事场景

队长不会只问一个人“你有什么好点子”。生成员先提出多个方向：改损失、改数据处理、改结构、改训练策略、改推理过程。此时的目标是覆盖可能性，而不是立即宣布冠军。

### 模块职责

生成阶段（GENERATING）的职责是从任务、基线、背景调研和历史经验中产生一组候选 Idea。

### 机制拆解

生成员可能先读取调查材料，再产出候选。每个候选至少要能说明：

- 想法名称和核心主张；
- 为什么可能改善当前问题；
- 预期改动的大致位置；
- 需要什么实验来验证；
- 可能遇到的风险。

系统把自由文本转换成 Idea 对象，之后批评、证据和评分都会写回同一张“方案卡”。

生成阶段的关键不是让所有 Idea 都成熟，而是保留足够的多样性，避免一开始就只沿着一个最容易描述的方向前进。

### 状态与循环

生成可以在一个内部迭代中发生，也可以在跨轮 Discovery 中再次发生。若当前轮次来自之前的失败经验，提示会强调避开重复失败；若来自有效结果，则会围绕已有方向扩展。

### 记忆与上下文

输入通常包含：

- 原始任务和基线；
- 可选 Deep Research 背景；
- 历史相似 Idea；
- 已知失败方法；
- 上一轮经验摘要；
- 当前轮的约束。

历史材料是“引导”，不是硬答案。一个曾经成功的方向仍需要在当前基线和指标上重新验证。

### 失败与恢复

- 生成数量不足：可以重新请求或降低非关键约束；
- 候选重复：由历史检索和 IdeaGraph 辅助去重；
- 候选过于模糊：留在后续反思中澄清，不直接当作可执行方法；
- 全部生成失败：Session 进入错误或采用明确的降级提示。

### 可观察产物

- 初始 Idea 集合；
- 每个 Idea 的原始描述和理由；
- 生成请求与响应；
- 生成阶段的草稿捕获记录。

### 输入—处理—输出小结

~~~text
输入：任务、基线、背景和历史经验
处理：扩大候选搜索面并结构化记录
输出：一组待批评的 Idea
~~~

## 第九章 反思：批评不是否定，而是制造可检验问题

### 故事场景

生成员提出“把注意力机制改成动态窗口”。反思员不直接说好或坏，而是追问：

- 动态窗口真的针对任务瓶颈吗？
- 计算量会不会失控？
- 数据规模能支撑这个改动吗？
- 有没有已有方法已经做过同样事情？
- 怎样设计实验才能把改进归因到这个改动？

### 模块职责

反思阶段（REFLECTING）把 Idea 转换成一组风险、假设和待验证问题，为资料检索、演化和实验设计提供方向。

### 机制拆解

反思通常从多个维度检查：

1. 新颖性和与已有工作的差异；
2. 与当前基线的相关性；
3. 可实现性和资源成本；
4. 可验证性和指标设计；
5. 失败模式与边界条件；
6. 是否存在证据缺口。

反思结果写回 Idea，而不是单独漂浮在聊天记录里。这样后续 Agent 能看到“这张方案卡被质疑过什么”。

多个 Idea 可以并行反思，但并发完成顺序不应改变逻辑结果；编排器会在进入下一阶段前汇总和对齐结果。

### 状态与循环

反思可能在初次生成后发生，也可能在方法规格和精炼方法形成后再次发生。后一种反思针对的是更具体的方法，而不是最初的模糊方向。

### 记忆与上下文

反思员接收 Idea 本身、任务约束、已有证据和历史失败摘要。它不应凭空填入实验数字。无法验证的判断应标记为假设或风险。

### 失败与恢复

- 一个 Idea 的反思失败：该 Idea 可被标记为信息不足，其他 Idea 继续；
- 并行任务部分失败：汇总时保留已完成批评，并明确缺失项；
- 反思文本互相矛盾：由后续排序或再反思处理，而不是静默覆盖。

### 可观察产物

- critique/批评文本；
- 风险和待验证问题；
- 每个 Idea 的反思状态；
- 反思阶段工具活动和日志。

### 输入—处理—输出小结

~~~text
输入：候选 Idea 与任务约束
处理：拆出假设、风险、证据缺口和实验问题
输出：可供查证与演化的批评信息
~~~

## 第十章 外部数据：把“听起来合理”变成“有依据的判断”

### 故事场景

资料员拿着反思员的问题去查论文、方法描述和引用关系。资料员不负责把候选直接判为成功，而是把“谁在什么条件下报告过什么”带回来。

### 模块职责

外部数据阶段（EXTERNAL_DATA）负责为 Idea 和方法补充文献证据、相关工作线索和引用信息。

### 机制拆解

资料员的工作可分为：

- 根据待验证问题生成检索方向；
- 获取论文或技术材料；
- 抽取与当前 Idea 直接相关的证据；
- 保存引用和来源；
- 将证据区分为支持、限制、背景或待核查。

初次研究阶段，证据通常写入 Idea 的 evidence 和 references；方法精炼阶段，新增证据可以进入 refine_evidence。这样可以区分“为什么值得尝试”和“具体方法怎样设计”。

Deep Research（DR）可在 Session 前先建立问题地图；ScholarAgent 则在具体阶段针对 Idea 查证。二者都是上下文来源，不等于论文阶段允许无限制地重新搜索。

### 状态与循环

外部数据任务可以并行处理多个 Idea。资料不足时，Idea 不一定立即淘汰，但排序时应降低置信度或标记风险。方法阶段可能再次进入外部数据，形成“具体化后再查证”的小循环。

### 记忆与上下文

检索结果会变成当前 Session 的证据，也可能进入长期研究记忆。后续 Agent 看到的不是整个网页，而是被整理后的证据、来源和与 Idea 的关联。

### 失败与恢复

- 搜索工具失败：保留“证据缺口”，不要把空结果当作没有相关工作；
- 单篇论文解析失败：其他来源仍可继续；
- 来源相互矛盾：记录矛盾，让排序和方法设计显式处理；
- 引用无法确认：不得把不确定条目包装成确定事实。

### 可观察产物

- evidence；
- references；
- refine_evidence；
- Scholar/DR 工具记录；
- 与 Idea 关联的来源摘要。

### 输入—处理—输出小结

~~~text
输入：Idea、批评和待验证问题
处理：检索、筛选、归类并保存证据
输出：带来源的研究依据和引用线索
~~~

## 第十一章 演化：从一张方案卡长出一棵候选树

### 故事场景

反思员发现“动态窗口”太宽泛。演化员把它拆成几个子方向：

- 只在高不确定区域扩大窗口；
- 用预算控制窗口变化；
- 训练时动态、推理时固定。

每个子方向都保留“我从哪张卡长出来”的关系。

### 模块职责

演化阶段（EVOLVING）根据批评、证据和已有 Idea 生成更具体或更有差异化的子想法。

### 机制拆解

演化不是简单改写标题，而是带着父子关系的搜索：

1. 读取父 Idea 的主张、批评和证据；
2. 找到需要修复或值得扩展的部分；
3. 产生一个或多个子 Idea；
4. 给每个子 Idea 记录 parent_id；
5. 把新想法放回同一 Session 的候选集合；
6. 让下一轮反思和排序继续处理。

父子关系使系统能回答“哪条路线来自哪次批评”，也允许在论文前选择最终方法时追溯灵感来源。

### 状态与循环

演化通常发生在每次内部迭代中。若排名结果仍不够成熟，经过自动反馈插槽后会重新生成；若候选已经足够集中，则进入方法开发。

### 记忆与上下文

演化员需要同时看到：

- 父 Idea；
- 对父 Idea 的批评；
- 外部证据；
- 同一轮其他候选的差异；
- 历史上相似但失败的方案。

这样才能避免生成一个换了名字、没有新内容的重复分支。

### 失败与恢复

- 某个父 Idea 不能演化：保留父 Idea，不影响其他分支；
- 子 Idea 结构不完整：标记为待澄清，不直接进入实验；
- 分支爆炸：由并发和 top ideas 限制控制搜索面；
- 子 Idea 被判断为重复：可归并、淘汰或保留其来源关系。

### 可观察产物

- 子 Idea；
- parent_id 和轮次关系；
- 演化理由；
- 新增方法描述；
- 分支级成功/失败记录。

### 输入—处理—输出小结

~~~text
输入：批评、证据和父 Idea
处理：修复缺口、扩展方向、建立父子关系
输出：更具体的候选 Idea 树
~~~

## 第十二章 排序：分数是继续探索的闸门，不是实验真理

### 故事场景

排序员给候选贴上优先级标签：某个方向新颖但风险高，某个方向稳妥但增益可能小，另一个方向证据充分但实现成本高。标签帮助队长分配下一轮资源，却不等于实验已经证明谁最好。

### 模块职责

排序阶段（RANKING）根据当前可见的描述、批评、证据和方法成熟度，为 Idea 评分并选择 top ideas。

### 机制拆解

排序综合考虑的可能因素包括：

- 与任务目标的相关性；
- 新颖性和差异化；
- 实现可行性；
- 实验可验证性；
- 风险与资源成本；
- 证据充分程度。

排序输出的本质是“下一步值得投入哪些候选”。真正的优劣仍要由实验指标和证据判断。

达到内部迭代上限后，top ideas 进入方法开发；未达到上限时，系统会进入自动反馈插槽，再开始下一次候选生成。

### 状态与循环

排序是 MAS 内部 loop 的决策点。它同时做两件事：

1. 选择本次保留的候选；
2. 判断继续探索，还是开始具体化方法。

### 记忆与上下文

排序员看到的是综合候选表，而非某个单独 Agent 的意见。历史成功/失败经验可以影响优先级，但不能绕过当前任务约束。

### 失败与恢复

- 某个候选缺少分数：可以标记为低置信度，不能默认为最高；
- 分数相近：保留多个候选，交给实验阶段区分；
- 排序调用失败：使用可审计的降级策略，或结束当前 Session 并保留结果；
- top ideas 为空：说明该轮没有可推进候选，应记录原因。

### 可观察产物

- 每个 Idea 的分数或排序信息；
- top ideas；
- 内部迭代计数；
- 下一状态决定；
- 排序请求与响应。

### 输入—处理—输出小结

~~~text
输入：候选、批评、证据和风险
处理：按继续投入的价值排序
输出：top ideas 与下一阶段选择
~~~

# 第五部：从方向到方法

## 第十三章 方法开发：把“研究想法”变成“实验协议”

### 故事场景

队长选出“动态窗口”方向后，不能马上让程序员开工。方法工程师要把它写成实验协议：

- 改哪一部分；
- 训练和推理分别怎么做；
- 需要哪些超参数或预算；
- 对照实验是什么；
- 何时算成功；
- 哪些结果会推翻假设。

### 模块职责

方法开发阶段（METHOD_DEVELOPMENT）只处理排名靠前的 Idea，把方向性的描述转成可执行、可比较、可解释的方法规格。

### 机制拆解

一个合格的方法规格至少要回答：

1. 机制：它相对基线改变了什么；
2. 作用位置：改变发生在数据、训练、模型结构还是推理流程；
3. 假设：为什么这个改变可能改善目标指标；
4. 实验：如何与 baseline 和其他候选公平比较；
5. 观测：需要保存哪些指标、日志和中间结果；
6. 风险：可能的失败模式是什么。

方法开发会再次收集相关证据，避免“可执行”只是凭空补细节。

### 状态与循环

方法开发不是论文写作，而是 Discovery 内部的具体化阶段。完成后通常回到外部数据或反思阶段，继续检查方法是否有证据缺口和内部矛盾。

### 记忆与上下文

方法工程师需要同时看到 top ideas、父子关系、批评、引用、任务约束以及实验资源边界。它不应看到并使用尚未验证的结果作为事实。

### 失败与恢复

- 方法无法落地：退回反思或淘汰该 Idea；
- 方法依赖缺少证据：进入外部数据阶段；
- 方法之间无法公平比较：记录实验设计风险，不强行合并；
- 方法规格过于复杂：可拆成核心版本和扩展版本。

### 可观察产物

- method details；
- 实验假设；
- 对照和指标计划；
- 资源与风险说明；
- 方法开发阶段的证据记录。

### 输入—处理—输出小结

~~~text
输入：top ideas、批评、证据和任务约束
处理：定义机制、实验协议和可验证假设
输出：可交给实验阶段的候选方法规格
~~~

## 第十四章 精炼：让方法规格经得起再次追问

### 故事场景

精炼员拿到方法规格后继续追问：这个机制在边界数据上还成立吗？文献是否支持这个假设？方法描述中的两个步骤是否互相冲突？如果删掉其中一个组件，实验是否仍能说明问题？

### 模块职责

精炼阶段（REFINING）把方法规格变成更完整、内部一致、带有证据边界的 refined method。

### 机制拆解

精炼主要做四件事：

- 根据新批评修补方法漏洞；
- 把外部证据和方法决策对齐；
- 删除无法由任务材料支持的夸大主张；
- 明确核心方法、可选组件和验证方式。

精炼后的方法才是实验和论文原材料之间的桥梁。它仍然不是实验结果，也不是论文最终措辞。

### 状态与循环

精炼是 MAS Session 的收束阶段。成功后进入 COMPLETED，失败则进入 ERROR 或回退到需要补证据的阶段。外层 Discovery 会把完成的 top ideas 交给实验分支。

### 记忆与上下文

精炼员读取全部可用的当前 Session 材料，但应优先引用结构化事实和已确认证据。历史经验只能作为设计参考。

### 失败与恢复

- 精炼后仍有关键证据缺口：保留缺口并阻止不负责任的“已验证”表述；
- 方法内部冲突：回到反思；
- 仅有一个组件成功：把组件边界写清，不把整体方案冒充成功。

### 可观察产物

- refined method；
- 方法与证据的对应关系；
- 未解决风险；
- MAS Session 的完成状态。

### 输入—处理—输出小结

~~~text
输入：方法规格、批评和 refine_evidence
处理：修补、收敛并标定主张边界
输出：可进入实验的最终候选方法描述
~~~

# 第六部：Agent—工具循环

## 第十五章 一个 Agent 为什么会调用工具很多次

### 故事场景

资料员想回答“这个方法是否已有先例”。他先搜索关键词，再打开结果，再读取摘要，再核对引用。每一步都可能产生下一步问题。模型不是一次生成终稿，而是在“请求—工具—结果—再请求”之间前进。

### 模块职责

工具循环（ModelToolLoop）负责让 Agent 在一个任务内持续使用工具，直到：

- Agent 返回可接受的普通文本；
- 没有新的工具调用；
- 达到工具调用或迭代上限；
- 出现无法恢复的错误。

### 机制拆解

一次循环可以拆为：

1. **发送当前请求**：包含任务、阶段上下文和已有工具结果；
2. **读取模型响应**：响应可能是普通文本，也可能包含一个或多个工具调用；
3. **逐个执行工具**：使用模型给出的工具名称和参数；
4. **包装结果**：成功结果和失败信息都转成模型可理解的返回；
5. **写入记录**：记录工具名、参数、结果和错误；
6. **继续请求**：把工具结果作为下一轮上下文，并沿用前一次响应上下文；
7. **判断停止**：满足结束条件就返回最终 Agent 输出。

工具失败不会自动等于整个 Agent 失败。模型可以看到“工具执行失败”的结果，决定换参数、换工具或明确说明证据不足。

### 工具循环图

~~~mermaid
flowchart TD
    A[Agent 请求] --> B[模型响应]
    B -->|普通文本| E[结束]
    B -->|工具调用| C[执行工具]
    C --> D[记录成功或错误]
    D --> A
~~~

### 状态与循环

工具循环是局部 loop，不能直接改变 MAS 的阶段状态。它的结果交回总协调者后，才可能让 WorkflowState 推进。

例如，ScholarAgent 连续调用三次搜索工具，只是在 EXTERNAL_DATA 状态内完成资料任务；只有当证据结果被汇总并写回 Idea，状态机才会考虑进入 EVOLVING 或 RANKING。

### 记忆与上下文

工具结果进入两处：

- 当前 Agent 的下一次模型请求；
- 可审计的工具使用记录和 ResearchDraft。

并不是所有工具结果都永久进入长期记忆。只有被阶段逻辑提取为 Idea 证据、实验记录或经验的内容，才会进入跨 Session 的记忆链路。

### 失败与恢复

- 参数错误：返回结构化错误，让 Agent 修正；
- 外部服务超时：可重试，超过上限后保留失败；
- 工具输出太大：应先摘要或裁剪，再进入上下文；
- 达到最大迭代数：返回当前可用结果，并标记可能未完成；
- 结果互相矛盾：保留多份记录，由上层判断。

### 可观察产物

- 工具调用名称；
- 调用参数；
- 返回结果；
- 错误和重试；
- Agent 最终输出；
- 工具循环的迭代次数和停止原因。

### 输入—处理—输出小结

~~~text
输入：Agent 当前问题与工具目录
处理：请求模型、执行工具、回填结果、重复判断
输出：可解释的 Agent 结果和完整工具轨迹
~~~

## 第十六章 工具调用和 MAS 的边界

### 故事场景

队员可以使用望远镜，但望远镜不会决定探险队是否进入下一个房间。工具是能力，状态机是流程，队长是编排。

### 模块职责

这一边界避免三个常见混淆：

1. 工具调用不是阶段推进；
2. Agent 输出不是实验事实；
3. 工具成功不是研究假设成功。

### 机制拆解

举一个完整例子：

~~~text
ReflectionAgent
  -> 请求检索工具
  -> 工具返回两篇相关材料
  -> Agent 提炼限制条件
  -> OrchestrationAgent 把限制写回 Idea
  -> 状态机决定是否进入 EVOLVING
~~~

每一箭头都是不同层次的动作。工具只负责“查到什么”，Agent 负责“如何解释当前任务中的意义”，编排器负责“结果是否足够推动阶段”，状态机负责“下一站在哪里”。

### 状态与循环

同一个阶段可以包含多轮工具循环；同一个 Agent 也可能在不同阶段被再次调用。不要用工具调用次数推断 Discovery 轮数。

### 记忆与上下文

工具结果首先是短期上下文。只有经阶段逻辑确认后，才变成 Idea evidence、实验指标或 experience。

### 失败与恢复

如果工具返回空结果，正确做法是把“空结果”记录下来，而不是把“没有证据”误写成“证明不存在”。如果工具误报，后续阶段仍需通过来源和实验核对。

### 可观察产物

工具轨迹、Agent 结论、状态变更和被写回的结构化字段。

### 输入—处理—输出小结

~~~text
输入：工具原始结果
处理：Agent 解释 + 编排器验收 + 状态机决策
输出：可推动流程的阶段事实
~~~

# 第七部：自动反馈插槽

## 第十七章 AWAITING_FEEDBACK 到底在等什么

### 故事场景

队伍走到一座自动补给站。站内没有工作人员，只有一个预先放好的反馈箱。调度器扫描当前状态，读取反馈文件，把“上一轮应该改变什么”交给下一轮，然后自动开门放行。

### 模块职责

自动反馈插槽（AWAITING_FEEDBACK）把一次内部迭代的结果交接给下一次生成。它让流程有一个明确的检查点，而不把“反馈”散落在任意模型消息里。

### 机制拆解

外层驱动器会：

1. 查询 MAS 当前状态；
2. 发现状态为 awaiting_feedback；
3. 读取预先准备的离线反馈 JSON；
4. 调用反馈入口；
5. 把反馈写入会话历史；
6. 自动恢复到下一次生成或指定阶段。

反馈可以描述：

- 哪些候选已经重复；
- 哪些风险尚未解决；
- 哪些指标或约束必须优先；
- 下一轮需要扩大还是收窄搜索。

### 状态与循环

它通常是 RANKING 和下一次 GENERATING 之间的边界。若排名已经足够成熟，则不经过该插槽，直接进入 METHOD_DEVELOPMENT。

### 记忆与上下文

反馈既是当前 Session 的短期上下文，也可能被经验生成器整理成跨轮经验。反馈的来源、时间和作用范围应该可追踪。

### 失败与恢复

- 反馈文件缺失：不能假装收到反馈；可使用无反馈的默认路径或停止当前内部迭代；
- 反馈格式无法解析：保留错误并避免推进到依赖它的阶段；
- 反馈与任务约束冲突：任务事实优先，冲突写入记录。

### 可观察产物

- awaiting_feedback 状态；
- 反馈 JSON；
- 反馈历史；
- 注入反馈后的下一阶段上下文。

### 输入—处理—输出小结

~~~text
输入：排名结果和离线反馈
处理：轮询、注入、记录并自动恢复
输出：下一次生成所需的明确反馈上下文
~~~

# 第八部：记忆、会话和断点恢复

## 第十八章 两种“记忆”不要混为一谈

### 故事场景

实验室有两套档案柜：

- 桌边的运行账本，记录今天这场讨论进行到哪里；
- 地下的长期资料库，记录过去许多任务的成功和失败模式。

把桌边账本丢进地下资料库，会找不到“今天从哪一步继续”；只看桌边账本，又无法避免重复过去的失败。

### 模块职责

Vegapunk 中至少有两层重要记忆：

1. **会话持久化记忆**：保证当前运行可恢复；
2. **长期研究记忆**：为后续轮次和后续 Session 提供经验。

### 机制拆解：会话持久化

会话持久化会把 Session 的结构化状态保存为任务目录中的轨迹或等价记录。阶段推进后，系统保存：

- 当前任务；
- Idea 集合；
- 状态；
- 轮次计数；
- top ideas；
- 反馈历史；
- 工具使用；
- 时间戳。

进程重启后，系统重新构造这些对象，继续从可信的阶段产物推进。

### 机制拆解：长期研究记忆

长期记忆由几个互补部分组成：

- **任务记忆（Task Memory）**：检索相似任务、想法和实验结果；
- **在线记忆（Online Memory）**：实验完成后立即保存本次结果；
- **IdeaGraph**：把历史 Idea 按语义相似度和关系连成图；
- **经验库（Experience Library）**：把 Idea 与实验记录配对，抽取成功/失败模式；
- **提示演化（PromptEvolver）**：根据累积经验调整后续生成提示。

如果有可用的嵌入模型，IdeaGraph 可以用语义相似度连接近似方向；如果没有，则可退回更简单的关键词或结构化追踪。

### 状态与循环

记忆写入不是最后一次性操作，而是分散在流程中：

- Session 阶段推进时保存会话状态；
- Idea 实验完成时写入在线记忆；
- 每轮结束时生成经验；
- 后续轮次读取经验并影响生成或提示。

### 记忆与上下文

记忆检索通常返回摘要或 top-k 相关记录，而不是把整个历史库塞入上下文。检索结果需要说明“为什么相关”，并保留来源指针，避免模型把相似案例误当成当前事实。

同一任务的历史结果可以在 fresh 模式中继续可见，因为 fresh 主要改变代码起点，不等于清空长期研究档案。

### 失败与恢复

- 嵌入模型不可用：检索或语义连边可能降级；
- 记忆目录损坏：当前 Session 仍可依靠本地账本和产物继续，但会失去部分历史建议；
- 重复记录：按绝对路径或稳定标识去重；
- 经验与当前任务不匹配：只作为低置信度提示，不直接改写任务目标。

### 可观察产物

- trajectory JSON；
- 历史 Idea 记录；
- IdeaGraph 关系；
- experience_library；
- 经验分析结果；
- 提示演化后的版本或摘要。

### 输入—处理—输出小结

~~~text
输入：当前阶段事件、历史记录和实验结果
处理：保存、检索、去重、建立关系、提炼经验
输出：可恢复的会话状态和可复用的研究知识
~~~

## 第十九章 断点恢复是怎样发生的

### 故事场景

夜间停电，队伍被迫离开。第二天，队长先看总账本，再检查最近一间房留下的样品，最后决定从“已完成反思、等待排序”继续，而不是重新走完整座山。

### 模块职责

恢复机制的目标是避免两种危险：

- 已经完成的实验被无意义地重跑；
- 实际未完成的阶段被状态记录误导而跳过。

### 机制拆解

恢复一般按可信度从高到低核对：

1. Launch 是否存在；
2. prompt 快照是否存在；
3. Session/实验目录是否存在；
4. 结构化结果是否完整；
5. 状态账本和产物是否一致；
6. 缺失步骤是重做、跳过还是降级。

已有 discovery_summary 或 session/run 目录时，可以从已完成部分继续。恢复不是把模型上下文原封不动复活，而是根据落盘事实重新构造上下文。

### 状态与循环

恢复可能重新进入当前阶段，也可能从下一阶段继续。选择依据是“阶段输出是否已经完整且可验证”，而不是仅看某个进程是否曾经返回。

### 记忆与上下文

恢复后的上下文由任务快照、会话账本、阶段产物、历史记忆和必要的日志摘要组成。原始长日志用于核对，不应无界地全部重新注入模型。

### 失败与恢复

若账本与产物冲突，保守地回到最近一个可验证检查点。若只缺少可选证据，则可以继续并记录警告；若缺少指标或代码快照，不应把候选标为成功。

### 可观察产物

恢复日志、跳过/重做决定、重新建立的 Session 状态以及新的时间戳。

### 输入—处理—输出小结

~~~text
输入：已有 Launch、账本和部分产物
处理：核对、重建上下文、选择安全检查点
输出：从可信位置继续的运行
~~~

# 第九部：实验是 Discovery 的现实检验

## 第二十章 Idea 进入候选实验工作台

### 故事场景

MAS 选出五张方案卡。工坊不会让五队人共用同一张桌子随意改代码，而是为每张卡复制一个独立工作台，保留同一个起始 baseline。

### 模块职责

候选实验阶段负责把 refined method 变成真实代码改动和运行结果，并把结果归因到具体 Idea。

### 机制拆解

每个候选工作台通常包含：

- Idea 摘要和方法说明；
- baseline 代码快照；
- 实验启动入口；
- run_0 基线结果；
- run_1、run_2 等候选尝试；
- 运行日志；
- 机器可读结果；
- 实验报告。

实验代理的工作可以抽象为：

1. 阅读 Idea 和基线；
2. 选择一次可控改动；
3. 保存代码和运行上下文；
4. 启动实验；
5. 读取指标和日志；
6. 判断是否需要修正；
7. 继续尝试或结束；
8. 把事实写入结果文件和报告。

本文不展开代码中的具体函数、变量或命令；关键是理解“每个候选有自己的证据边界”。

### 状态与循环

候选实验内部有一个实验重试 loop：

~~~text
基线
  -> 设计改动
  -> 运行
  -> 读取结果
  -> 诊断成功/失败
  -> 接受、修正或回到下一次尝试
~~~

它和 MAS loop 的区别是：MAS loop 在想法空间中搜索；实验 loop 在代码和指标空间中验证。

### 记忆与上下文

实验工作台接收：

- 当前轮 baseline；
- refined method；
- 任务指标和优化方向；
- 资源限制；
- 过去失败经验。

它不应直接把其他候选未验证的结果当作当前候选的输入。

### 失败与恢复

- 代码改动无法运行：记录失败原因，保留工作台；
- 实验超时或资源不足：区分“方法失败”和“执行未完成”；
- 指标缺失：不能计算可靠改进；
- 某次尝试失败：可以继续同一候选的下一次尝试，或结束该候选；
- 候选整体失败：不拖垮其他工作台。

### 可观察产物

- 候选实验目录；
- run_0 与 run_N；
- final_info.json 等机器可读指标；
- experiment_report.txt 等叙述性材料；
- log.txt；
- 候选代码快照；
- 成功/失败标志和错误信息。

### 输入—处理—输出小结

~~~text
输入：refined method、baseline 和指标
处理：隔离改动、运行、读取、比较和重试
输出：候选级实验事实、代码和证据
~~~

## 第二十一章 run_0、run_N 和 baseline 比较

### 故事场景

每个工作台都先拍一张“未改动照片”，这就是 run_0。之后每做一次改动，就拍一张新的照片。没有 run_0，队伍只能说“这次分数是 0.82”，却不能说它比什么更好。

### 模块职责

运行级记录负责建立公平比较的参照系，计算候选相对 baseline 的改进，而不是只展示一个孤立数字。

### 机制拆解

- run_0：该候选开始实验时的基线结果；
- run_N：第 N 次具体改动或运行；
- final_info.json：机器可读的指标和结果元数据；
- experiment_report.txt：对运行过程的叙述性总结；
- log.txt：更完整的过程和错误线索。

系统会从机器可读结果中读取指标，比较候选与 baseline 的变化。多个指标需要按任务目标综合，形成整体改进率或等价的比较摘要。

“整体改进”是决策辅助，不应抹掉单个指标的真实变化。例如平均分提高但延迟变差，报告中仍应保留两者。

### 状态与循环

同一候选可以多次运行，直到达到尝试上限、找到可接受结果、资源耗尽或明确判断方向不值得继续。

### 记忆与上下文

每次运行的事实可以进入在线记忆和经验生成器。后续实验代理可看到同一候选的历史尝试，但不同候选之间的结果通常通过上层汇总传递，而不是直接共享工作目录。

### 失败与恢复

- final_info 缺失：结果只能标记为不完整；
- 报告与机器结果矛盾：机器可读指标优先，矛盾写入警告；
- run_0 不是当前真正基线：需要核对工作台快照，不能盲算改进；
- 指标方向不明：无法安全比较时，保留原始值并标记选择风险。

### 可观察产物

运行目录、指标文件、报告、日志、比较摘要和选择依据。

### 输入—处理—输出小结

~~~text
输入：run_0、run_N 和任务指标方向
处理：核对事实并计算相对变化
输出：可审计的候选性能比较
~~~

## 第二十二章 incremental baseline：上一轮结果怎样变成下一轮起点

### 故事场景

某轮五个工作台中，第三个候选确实更好。队长不会把全部工作台都搬走，只会把第三个候选的代码、基线指标和科学任务需要的输出，封存为下一轮的起点。

### 模块职责

incremental 机制负责把跨轮实验结果转化为下一轮可用 baseline，同时保留选择的来源和性能依据。

### 机制拆解

1. 汇总本轮成功和失败候选；
2. 比较候选相对各自 baseline 的改进；
3. 选出本轮最佳结果；
4. 更新下一轮的代码起点；
5. 对科学任务同步需要的 outputs、report 等材料；
6. 在汇总中记录最终最佳路径和性能。

这不是“把所有模型参数平均一下”，而是选择一个完整、可继续运行的候选工作区作为下一轮起点。

### 状态与循环

该机制发生在外层 Round 之间，不改变当前 MAS Session 已经完成的状态。

### 记忆与上下文

下一轮既看到新的代码 baseline，也可以看到本轮经验。代码反馈回答“现在站在哪个实现上”，经验反馈回答“下一轮应该怎样探索”。

### 失败与恢复

- 没有成功候选：保留旧 baseline；
- 最佳候选缺少必要输出：不能直接作为科学任务 baseline；
- 选择过程失败：记录选择错误，不静默替换；
- 恢复时发现 baseline 已更新：以汇总和路径校验为准。

### 可观察产物

最终最佳代码路径、性能摘要、baseline 更新记录和 discovery_summary 中的 incremental 信息。

### 输入—处理—输出小结

~~~text
输入：本轮候选实验结果
处理：比较、选择、封存并更新基线
输出：下一轮代码起点和可追溯选择记录
~~~

## 第二十三章 实验模式和报告模式

### 故事场景

工坊有两种工作单：

- 实验模式：真的修改代码、启动运行、读取指标；
- 报告模式：已有结果或外部执行记录，主要负责整理和汇总。

主故事采用实验模式，因为它最完整地展示“想法如何被现实检验”。

### 模块职责

模式分支决定 Discovery 在候选 Idea 之后是否进入真实执行环节，以及最终汇总使用什么证据。

### 机制拆解

**实验模式**强调：

- 独立候选工作台；
- baseline 与 run_N 比较；
- 代码、指标、日志和报告的共同产出；
- 成功候选推动下一轮 baseline。

**报告模式**强调：

- 读取已有结果或任务提供的材料；
- 组织候选状态和发现；
- 避免把没有执行过的改动写成已验证实验。

无论哪种模式，进入 PaperOrchestra 前都要形成统一的 discovery_summary 和可交接材料。

### 状态与循环

报告模式可以跳过实验重试 loop，但仍需完成结果汇总和交接前校验。实验模式则完整经过候选执行和比较。

### 记忆与上下文

报告模式使用已有记录作为上下文；不能凭报告文字反推缺失的机器结果。实验模式则从工作台和运行文件生成事实。

### 失败与恢复

- 报告材料缺少证据：明确标记未知；
- 实验和报告材料矛盾：回到机器可读结果核对；
- 模式配置错误：在进入候选阶段前失败，而不是事后伪造结果。

### 可观察产物

模式标识、候选结果汇总、报告或实验文件、失败原因和交接材料。

### 输入—处理—输出小结

~~~text
输入：Idea 与执行条件/已有结果
处理：实验验证或报告汇总
输出：统一格式的 Discovery 结果
~~~

# 第十部：ResearchDraft——把过程留下来，但不冒充最终论文

## 第二十四章 ResearchDraft 是什么

### 故事场景

工坊有一本“原始研究记录本”。书记员不替队员润色，只按发生顺序追加：谁提出了什么请求、工具返回了什么、实验输出了什么、哪里出错了。

### 模块职责

研究草稿捕获器（ResearchDraft）的职责是保存原始、可观察、可追溯的研究过程，供后续复盘和 PaperOrchestra 使用。

### 机制拆解

它通常在 Launch 下建立 manuscript/draft.md，并以追加方式保存研究块：

- 不重写旧块；
- 不覆盖历史；
- 不把多个 Agent 的输出偷偷合并为一段“看似统一”的结论；
- 对输入、输出、工具调用和工具结果做事件级捕获；
- 可以附带 stdout、stderr、日志和异常。

这里的“原始”不等于“把隐藏思维过程全部写出来”。它保存的是可观察上下文：请求、响应、工具事件、日志和错误，不声称捕获模型的不可见内部推理。

### 状态与循环

Draft 捕获贯穿 Discovery 的可观察边界。在 PaperOrchestra 接手前，它是原始研究记录之一；论文阶段的正式写作不应继续把所有运行噪声无差别追加进去。

### 记忆与上下文

Draft 是长记录，当前 Agent 通常只看到经过编排的摘要或相关片段。PaperOrchestra 可以从 Draft、ideas、实验报告和机器结果生成更稀疏的论文材料。

### 失败与恢复

- 某个捕获事件写入失败：应留下警告，并尽量保留其他产物；
- Draft 断裂：不能把后续记录伪装成连续历史；
- 日志包含敏感信息：在交付前按项目边界处理，不将无关凭据带入论文材料。

### 可观察产物

- manuscript/draft.md；
- Agent 输入/输出块；
- 工具调用和结果块；
- stdout/stderr；
- 异常和日志块。

### 输入—处理—输出小结

~~~text
输入：可观察研究事件
处理：按顺序追加、标注来源、保留错误
输出：可追溯的原始研究记录
~~~

## 第二十五章 为什么 ResearchDraft 不能直接当论文

原始记录包含大量不适合论文的内容：

- 重试和失败；
- 工具参数和冗余输出；
- 不成熟的假设；
- 被淘汰的候选；
- 暂时性的错误解释；
- 运行时日志。

它的价值是证明“过程发生过什么”，不是提供“正文应该怎么写”。论文材料需要重新做三件事：

1. 区分计划、观察和结论；
2. 只保留与最终候选有关的证据；
3. 把数字和主张连接到可回查来源。

因此，ResearchDraft 是原始矿石，PaperOrchestra 是冶炼和装配工坊。

# 第十一部：实验产物如何成为研究证据

## 第二十六章 产物不是越多越好，而是要知道谁能证明什么

### 故事场景

队伍带回一箱材料。队长发现：

- 任务信能说明研究目标；
- Idea 卡能说明方法设想；
- final_info 能说明数字；
- report 能说明过程；
- log 能帮助查错；
- Draft 能说明协作轨迹。

不同材料不能互相替代。

### 产物证据层级

| 材料 | 能证明什么 | 不能单独证明什么 |
| --- | --- | --- |
| prompt.json | 任务背景、目标、约束 | 方法确实有效 |
| ideas.json | 候选设计和方法动机 | 实验已经运行成功 |
| notes.txt | 候选开始时的摘要 | 最终代码一定符合摘要 |
| code/ | 候选代码快照 | 代码一定产生了某个指标 |
| run_0 | 基线结果 | 改动后的提升 |
| run_N/final_info.json | 某次运行的机器可读结果 | 结果为何产生、是否可复现全部细节 |
| experiment_report.txt | 运行过程的叙述总结 | 其中数字一定没有错 |
| log.txt | 过程、错误和线索 | 适合直接放入正文 |
| discovery_summary.json | 全局索引和轮次汇总 | 替代所有底层原始结果 |
| ResearchDraft | 可观察协作过程 | 最终科学结论 |

### 机制原则

论文编排时应优先从结构化事实和可回查文件提取数字，再用叙述性材料解释过程。若 report 与 final_info 不一致，应保留冲突并以机器可读结果为主要事实源。

### 输入—处理—输出小结

~~~text
输入：不同层级的研究产物
处理：按证据能力归类和交叉核对
输出：可用于论文的事实、解释和来源关系
~~~

# 第十二部：PaperOrchestra 如何接手

## 第二十七章 Discovery 和论文写作的交接边界

### 故事场景

探险队回到工坊门口，把总档案交给论文编排组。编排组不会在队伍还在山里时改实验，也不会把未完成的 Idea 当成终稿。

### 模块职责

交接机制负责在 Discovery 完成后，把 Launch 目录中的任务、候选、实验和证据转换成 PaperOrchestra 可消费的论文输入。

### 机制拆解

交接前的基本校验包括：

- Launch 目录存在；
- prompt.json 存在；
- discovery_summary.json 存在；
- summary 中有完成的 rounds 或等价的轮次结果；
- 最终候选和实验材料能够被定位。

确认后，系统创建独立的 PaperOrchestra Run 目录。论文运行有自己的日志、配置快照和状态，不与候选实验工作台混写。

### 状态与循环

交接通常在所有 Discovery 轮次结束并写入 summary 后触发一次。论文阶段的失败不会把已经完成的 Discovery 结果改判为失败；它会作为独立的论文运行失败或警告记录。

### 记忆与上下文

PaperOrchestra 接收的是整理后的研究材料，而不是自动获得 MAS 的全部对话。它可以使用：

- 任务提示；
- 选中的 Idea 和方法；
- 实验报告；
- final_info；
- ResearchDraft；
- 轨迹和错误记录。

### 失败与恢复

- 缺少 prompt 或 summary：交接前失败；
- 候选路径失效：保留选择错误并停止论文运行；
- PaperOrchestra 运行失败：保留 Discovery Launch，可重新尝试论文阶段；
- 论文输出为空或损坏：不能只因为进程退出就宣称交付成功。

### 可观察产物

- paper_orchestra_runs 下的运行目录；
- 论文运行配置；
- 选中候选记录；
- 原始材料；
- stdout/stderr；
- TeX、PDF、警告和结构化错误。

### 输入—处理—输出小结

~~~text
输入：完成的 Discovery Launch
处理：校验、选择、投影和建立论文运行
输出：独立可审计的 PaperOrchestra 输入包
~~~

## 第二十八章 终局候选选择：为什么不是“最后一个 Idea”

### 故事场景

最后一轮可能有多个成功候选。编排组要问：哪个候选最适合讲成一篇完整论文？它是否有足够实验支撑？选择依据是什么？如果指标方向不明显，是否需要依据任务材料推断选择标准？

### 模块职责

终局候选选择负责把“Discovery 产生的候选集合”收敛成论文主候选，并保留选择来源和理由。

### 机制拆解

选择通常综合：

- 最终轮次和成功状态；
- 相对 baseline 的性能；
- 任务中声明的主要指标和优化方向；
- 方法描述是否完整；
- 实验材料是否足够；
- 候选选择的可审计性。

“排名最高”不一定等于“论文最适合”。一个分数略低但证据完整、归因清楚的候选，可能比只有一项孤立提升的候选更适合作为论文中心。

### 状态与循环

如果选择不确定，系统应使用明确的回退规则或保留警告，而不是循环猜测直到得到想要的候选。选定后，后续材料都围绕该候选装配。

### 记忆与上下文

选择器读取 summary、Idea、实验指标和任务提示。它不应使用候选未提供的外部知识来发明“更好”的标准。

### 失败与恢复

- 没有成功候选：可以交付失败报告或明确的空结果，不伪造论文；
- 指标方向缺失：从任务材料推断并记录理由；
- 选择依据冲突：保留候选选择溯源，允许后续审计。

### 可观察产物

- 终局候选选择记录；
- 主指标和优化方向；
- 选择理由；
- 被选中的 Idea、代码和实验路径。

### 输入—处理—输出小结

~~~text
输入：summary、候选 Idea、实验事实和任务目标
处理：应用选择标准并记录溯源
输出：论文主候选及其选择依据
~~~

## 第二十九章 原始材料：idea_sparse 与 experimental_log

### 故事场景

编排组先把一箱原始材料整理成两本薄册：

- idea_sparse.md：只讲最终方法、动机和核心贡献；
- experimental_log.md：只讲实验事实、运行、指标、消融和失败边界。

薄册故意比原始 Draft 稀疏，因为论文 Agent 需要清晰的事实边界。

### 模块职责

原始材料投影负责把候选和实验目录转换成 PaperOrchestra 的稳定输入，不让论文阶段直接从杂乱日志中猜结论。

### 机制拆解

**idea_sparse.md** 通常汇集：

- 任务背景和问题；
- 选定方法；
- 核心机制；
- 主要贡献候选；
- 方法与基线的差异；
- 仍然存在的限制。

**experimental_log.md** 通常汇集：

- baseline 与各次 run；
- 指标和变化；
- 实验配置摘要；
- 消融或对照；
- 成功与失败；
- 结果来源和路径。

系统还会把 prompt、notes、实验报告、final_info、日志和 traceback 等整理到论文运行目录，便于追溯。

### 状态与循环

材料投影通常是一次确定性整理，但若候选选择改变，应重新生成两本薄册，避免正文和事实源不一致。

### 记忆与上下文

投影层读取 Discovery 产物，不重新运行 MAS，也不替代实验。它的目标是减少论文 Agent 看到的噪声，同时保留来源。

### 失败与恢复

- idea_sparse 为空：方法主线不足，不能可靠写正文；
- experimental_log 缺少数字：论文只能写有限结论；
- 来源路径失效：记录警告，不用自由文本补齐；
- 两本薄册互相矛盾：回到候选选择或事实核对。

### 可观察产物

- idea_sparse.md；
- experimental_log.md；
- 选定候选的材料链接；
- 输入清单和生成日志。

### 输入—处理—输出小结

~~~text
输入：Discovery 的结构化结果和原始材料
处理：筛选、压缩、标注来源、分离方法与实验事实
输出：PaperOrchestra 的稳定输入薄册
~~~

## 第三十章 论文编排阶段：从材料到正文

### 故事场景

论文工坊不是一个“写作模型”，而是一条装配线：

1. 规划师设计论文骨架；
2. 资料编排员安排相关工作和引用线索；
3. 章节写作者按材料填充各节；
4. 内容审查员检查主张与证据；
5. 排版审查员检查格式、编译和版式。

### 模块职责

PaperOrchestra 负责把研究材料装配为结构化论文，并在内容和格式层面循环修正。

### 机制拆解

典型阶段包括：

1. **大纲规划**：根据方法和实验材料确定摘要、引言、方法、实验、结论和附录结构；
2. **文献与图表规划**：从已提供材料中明确需要的证据、引用和图表；
3. **章节写作**：按大纲生成 TeX 章节；
4. **内容精修**：检查事实、主张范围、证据覆盖和前后一致性；
5. **格式精修**：修正模板、引用、图表位置和排版问题；
6. **编译与审查**：生成英文 TeX/PDF，并检查输出结构；
7. **中文伴侣（可选）**：基于英文定稿生成中文 TeX/PDF 伴侣。

论文 Agent 的知识边界很重要：当前材料是它的事实来源。它不应从训练记忆里补写实验数字、作者机构、未提供的结果或未经材料支持的强结论。

### 状态与循环

PaperOrchestra 有自己的论文 refinement loop：

~~~text
大纲
  -> 写作
  -> 内容审查
  -> 修订
  -> 编译
  -> 格式审查
  -> 必要时修订
  -> 最终交付
~~~

这是论文阶段的 loop，不要与 MAS 的 Idea 演化 loop 混淆。

### 记忆与上下文

每一阶段接收前一阶段的正式产物和原始材料索引。章节写作者不需要重新阅读全部工具日志；内容审查员则需要能回查关键事实来源。

### 失败与恢复

- 大纲无法覆盖实验事实：回到大纲阶段；
- 正文出现无来源数字：内容精修应删除、改弱或标记缺口；
- 编译失败：进入格式修正；
- PDF 结构异常：即使进程退出正常，也不能交付；
- 中文伴侣失败：英文主论文仍可独立报告状态。

### 可观察产物

- 大纲；
- TeX 源文件；
- 章节和修订记录；
- 编译日志；
- PDF；
- warnings；
- 中文 TeX/PDF 伴侣（若启用）。

### 输入—处理—输出小结

~~~text
输入：idea_sparse、experimental_log 和模板/约束
处理：规划、写作、审查、修订、编译
输出：可检查的 TeX、PDF 和状态报告
~~~

## 第三十一章 为什么 PaperOrchestra 要检查 PDF，而不是只看退出码

一个进程“返回成功”只说明调用层没有捕获到异常，不说明论文真的生成了。

因此交付前至少要检查：

- TeX 是否非空；
- PDF 是否具有有效的 PDF 文件结构；
- 末尾是否完整；
- 编译日志中是否有未解决错误；
- 论文运行状态是否与文件存在情况一致。

这是一种“产物验证”思维：

> 以交付物是否成立为准，而不是以某个子进程是否说自己成功为准。

# 第十三部：一次完整端到端回放

## 第三十二章 故事案例：改进一个已有的图像分类基线

下面的数值和名称是帮助理解机制的示意，不是对某次真实任务结果的承诺。

### 任务信

研究者提供：

- 一个已有图像分类算法和可运行代码；
- 数据集和主指标；
- 目标：在保持推理成本可接受的情况下减少错误分类；
- 约束：不能改变数据许可和基础运行入口。

### 第 0 步：建立 Launch

系统把任务材料整理为 prompt 快照，记录外层轮数和 loop mode，建立 Launch 目录。此时还没有论文，也没有“最终方法”。

### 第 1 步：第一轮 MAS

生成员提出四个方向：

1. 调整损失函数；
2. 在训练阶段使用难例重加权；
3. 增加轻量级特征校准；
4. 修改推理时的置信度阈值。

反思员发现：

- 方向 1 可能只改善平均指标，却伤害少数类；
- 方向 2 需要检查数据分布偏差；
- 方向 3 需要证明额外模块不会显著增加成本；
- 方向 4 容易把阈值调参误当作模型改进。

资料员补充相关方法和限制。演化员把方向 2 拆成“按类别重加权”和“按不确定性重加权”两个子 Idea。排序员选择前三个进入方法开发。

### 第 2 步：方法开发与精炼

方法工程师为“轻量级特征校准”写出协议：

- 只增加一个小型校准步骤；
- 训练和推理位置明确；
- 对照组包含原始 baseline；
- 需要报告准确率、少数类指标和推理开销。

精炼员发现原始描述没有定义校准失败条件，于是加入边界和消融要求。MAS Session 完成，输出 refined methods。

### 第 3 步：候选实验

系统为三个候选建立三个独立工作台，每个都复制同一个 run_0。

- 候选 A 的第一次改动运行失败，日志显示资源不足；
- 候选 B 成功运行，但主指标提高、少数类指标下降；
- 候选 C 的主指标和少数类指标都改善，推理开销略增。

汇总时，系统不把 A 的资源失败写成“方法无效”，也不把 B 的单项提升写成全面胜出。C 的结果最符合任务目标，成为本轮 best result。

### 第 4 步：incremental 反馈

若使用 incremental，C 的代码和必要输出成为第二轮 baseline。与此同时，经验生成器记录：

- “只调阈值”的方向需要更严格的对照；
- 轻量校准需要单独报告开销；
- 少数类指标必须保留。

下一轮生成提示会看到这些经验，但不会直接相信 C 在所有数据上都有效。

### 第 5 步：第二轮内部 loop

新的 MAS Session 以 C 的代码为起点。生成员围绕校准机制提出更细的变体，反思员针对开销和泛化风险查证，排序员选出两个候选。实验阶段用新的 run_0 比较它们。

经过若干 Discovery Round，系统写入 discovery_summary，索引每轮候选、成功数、失败数和最终最佳结果。

### 第 6 步：交给 PaperOrchestra

交接前检查 prompt 和 summary。终局选择器确认 C 的改进链和证据最完整，生成：

- idea_sparse.md：描述轻量校准方法和贡献边界；
- experimental_log.md：列出每轮 baseline、run、指标、消融和失败情况。

论文工坊据此规划大纲、编排相关工作、写章节、检查主张和编译 TeX。

### 第 7 步：最终交付

英文 TeX 编译成功并生成有效 PDF。若开启中文伴侣，则再生成中文 TeX/PDF。最终交付包同时保留：

- 论文文件；
- 论文运行日志；
- 候选选择依据；
- 原始材料；
- Discovery 汇总；
- 警告和未解决限制。

这就是“从一句话到论文”真正的端到端路径：中间没有哪一步可以被一句漂亮的模型回复完全替代。

# 第十四部：常见混淆与正确理解

## 第三十三章 MAS、loop、状态、记忆、工具分别是什么

| 容易混淆的词 | 正确理解 | 一个判断问题 |
| --- | --- | --- |
| MAS | 多个有职责边界的 Agent 加上协调和共享设施 | “谁负责哪一阶段？” |
| loop | 某一层的重复推进机制 | “重复发生在轮次、阶段、工具还是实验？” |
| WorkflowState | 当前阶段的枚举状态 | “现在流程在哪个房间？” |
| WorkflowSession | 保存阶段和 Idea 的运行账本 | “中断后从哪里继续？” |
| Memory | 跨时间保存或检索的资料 | “过去什么信息会影响现在？” |
| Tool | Agent 可调用的外部能力 | “模型要借什么仪器获得结果？” |
| Idea | 研究候选和其演化关系 | “这个方向为什么值得验证？” |
| Experiment Result | 运行产生的事实 | “代码实际跑出了什么？” |
| PaperOrchestra | 论文材料编排、写作、审查和编译 | “如何把证据组织成交付物？” |

## 第三十四章 五个 loop 的时间尺度

| loop | 时间尺度 | 主要对象 | 结束条件 |
| --- | --- | --- | --- |
| Discovery Round Loop | 一次完整研究运行的多轮 | baseline、Idea、候选实验 | 所有外层轮次完成或终止 |
| MAS Stage Loop | 一个 Session 的多次想法迭代 | Idea、critique、evidence、ranking | 达到内部上限并进入方法阶段 |
| Agent-Tool Loop | 一次 Agent 任务内 | 请求、工具调用、结果 | 无工具调用、达到上限或错误 |
| Experiment Retry Loop | 一个候选工作台内 | 代码快照、run_0、run_N、指标 | 找到可接受结果、达到上限或失败 |
| Paper Refinement Loop | 论文写作运行内 | 大纲、TeX、审查意见、PDF | 内容/格式检查通过或报告失败 |

判断 loop 时，先问“它重复的对象是什么”，再问“它由谁控制”。

## 第三十五章 排序高、实验好、论文适合不是一回事

这三个判断处在不同层次：

1. **排序高**：当前描述和证据下，值得继续投入；
2. **实验好**：在明确 baseline、运行和指标下，实际产生改进；
3. **论文适合**：有方法、动机、对照、结果和限制，能形成完整证据链。

一个 Idea 可以排序高但实验失败；一个候选可以实验有亮点但证据不足；最终论文候选要同时考虑结果和可叙述性。

# 第十五部：失败、警告与自动恢复

## 第三十六章 一张恢复矩阵

| 故障位置 | 发生了什么 | 合理处理 | 不应做什么 |
| --- | --- | --- | --- |
| 任务准备 | 缺少必要 prompt | 在 Launch 前报错 | 用模型猜任务约束 |
| 生成阶段 | 候选不足或格式不全 | 重试、降级或记录缺口 | 把模糊文本当成熟方法 |
| 反思/检索 | 单个 Idea 失败 | 隔离分支、保留其他结果 | 让一个候选拖垮整轮 |
| 工具循环 | 工具报错 | 将错误回填，允许修正 | 把错误当空白成功 |
| 实验运行 | 超时、资源不足 | 区分未完成与方法失败 | 用空指标计算提升 |
| 指标汇总 | 机器结果与报告矛盾 | 以可回查事实核对并留警告 | 静默覆盖冲突 |
| baseline 更新 | 没有可靠 best result | 保留旧 baseline | 任意替换代码起点 |
| 状态恢复 | 账本和文件不一致 | 回到最近可信检查点 | 只看状态字符串跳过产物 |
| 论文交接 | 缺 summary 或候选 | 交接前失败 | 从零编造论文 |
| 编译/审查 | TeX/PDF 不完整 | 进入精修或报告失败 | 只看进程退出码 |

## 第三十七章 全自动不等于无检查

没有人工介入时，检查必须由机制承担：

- 状态机检查阶段合法性；
- 结构化文件检查产物是否存在；
- 工具循环检查调用上限；
- 指标层检查 baseline 和方向；
- 论文层检查 TeX/PDF；
- 日志和 Draft 提供审计线索。

自动化的目标不是消灭判断，而是把判断点变成可重复、可记录的规则和阶段。

# 第十六部：如何阅读一次真实运行

## 第三十八章 推荐的观察顺序

当你拿到一个 Launch 目录，不要先打开最长的日志。按以下顺序阅读：

1. **prompt.json**：确认任务目标、数据、指标、约束；
2. **discovery_summary.json**：看跑了几轮、有哪些候选、谁成功；
3. **每轮 ideas.json**：看候选是怎样提出和演化的；
4. **候选 notes.txt**：快速理解候选意图；
5. **run_0 与 run_N/final_info.json**：核对基线和指标事实；
6. **experiment_report.txt**：理解过程叙述；
7. **log.txt 与 traceback**：只在需要解释失败时深入；
8. **manuscript/draft.md 与 traj.json**：复盘 Agent、工具和阶段轨迹；
9. **paper_orchestra_runs**：查看论文材料、TeX、PDF 和警告。

这个顺序体现了“先目标，后汇总，再事实，最后过程”的证据原则。

## 第三十九章 看懂一个候选的最短路径

对任意一个候选 Idea，依次回答：

~~~text
它提出了什么？
  -> 它被批评过什么？
  -> 哪些证据支持或限制它？
  -> 方法规格具体是什么？
  -> run_0 是什么？
  -> run_N 实际跑出了什么？
  -> 相对 baseline 改善了什么，牺牲了什么？
  -> 它为何进入或没有进入论文？
~~~

如果某一问没有材料，正确结论是“缺证据”，不是凭文本补全。

# 结语：最终论文为什么不是一次模型输出

如果只记住一件事，请记住这句话：

> Discovery 把不确定性逐层搬运到可以检查的产物里，PaperOrchestra 再把这些产物组织成论文。

研究目标最初只是一个愿望。它要经过：

- 任务规范化，才知道要解决什么；
- 多智能体分工，才不会让一个角色同时发明、批评和证明自己；
- 状态机，才知道当前阶段和恢复位置；
- loop，才有机会从失败中继续；
- 工具循环，才可以获得外部数据和真实执行结果；
- 记忆，才不会每一轮都失去过去；
- 实验工作台，才把语言方案交给代码和指标检验；
- ResearchDraft，才保留可观察过程；
- PaperOrchestra，才把事实、主张、图表和章节装配为正式论文。

所以，最终的 TeX 和 PDF 并不是“最后一个模型回复的放大版”。它们是一个有边界、有状态、有反馈、有记忆、有证据校验的自动研究流程留下的压缩结果。

当你以后看到一篇由该流程生成的论文，可以反向追问：

~~~text
这个主张来自哪张 Idea 卡？
  -> 它经过了哪些批评和证据？
  -> 哪个候选实验验证了它？
  -> 与哪个 baseline 比较？
  -> 数字来自哪个 run？
  -> 为什么它被选作终局候选？
  -> PaperOrchestra 在哪些阶段把它写进了论文？
~~~

能回答这些问题，才算真正理解了从输出到最终论文的全流程。
